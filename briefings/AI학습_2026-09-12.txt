📚 오늘의 학습 주제 : 심화 21일차 · Git/GitHub 자동 배포(CI/CD), 실제 GitHub Actions 워크플로우 파일을 한 줄씩 뜯어보기 (2026-09-12)

📌 어제 배운 내용과의 연결
어제는 같은 비밀번호(API 키)를 로컬 .env, Vercel 환경변수, GitHub Secrets라는 세 금고에 각각 등록해야 한다는 것을 배웠는데, 그중 GitHub Secrets는 대체 언제, 누가, 어떤 순서로 열어서 쓰는 것인지 궁금했을 것입니다. 오늘은 바로 그 순간, 즉 코드를 push하는 순간부터 배포가 끝나는 순간까지 실제 워크플로우 파일이 한 줄씩 어떻게 실행되는지를 봅니다.

🎯 오늘 배울 개념
GitHub Actions 워크플로우 파일(Workflow file, 저장소에 어떤 사건이 생기면 어떤 작업을 어떤 순서로 실행할지 미리 적어두는 설정 파일)이 실제로 어떤 구조를 가지고 있고, 그 안의 job(작업 단위)과 step(작업 안의 세부 단계)들이 위에서부터 순서대로 실행되면서 앞 단계가 실패하면 뒷 단계, 특히 배포 단계가 아예 실행되지 않는 구조

━━━━━━━━━━━━━━━━━━━━

어제까지는 관리소가 "매뉴얼이 바뀌면 알아서 게시판에 붙여준다"는 결과만 이야기했다면, 오늘은 그 관리소 안에 실제로 붙어 있는 작업 지시서 원본을 펼쳐봅니다. 이 지시서에는 이런 식으로 적혀 있습니다. 첫째, 어떤 사건이 생기면 이 지시서를 실행할지(트리거, 예를 들어 "누군가 서고 원본을 고쳐서 제출하면"). 둘째, 그 사건이 생겼을 때 어느 작업대(러너, Runner, 워크플로우가 실제로 실행되는 임시 컴퓨터 한 대)를 새로 빌려서 쓸지. 셋째, 그 작업대 위에서 순서대로 처리할 세부 지시 목록. 관리소 직원은 이 지시서를 위에서부터 한 줄씩 읽어 내려가며 그대로 따라 하는데, 만약 셋째 줄인 "품질 검사" 단계에서 원본에 오탈자가 발견되면, 그다음 줄인 "게시판에 붙이기"는 아예 시도하지도 않고 작업을 중단합니다. 즉 지시서는 실패한 줄 다음부터는 실행되지 않는 순차 목록이며, 이 덕분에 검사를 통과하지 못한 매뉴얼이 게시판에 걸리는 사고가 애초에 막힙니다. 그리고 지시서 중간에 "금고에서 이 비밀번호를 꺼내 쓰라"는 지시가 있으면, 그 순간에만 관리소가 어제 등록해둔 GitHub Secrets 금고를 열어 값을 건네주고, 지시서 자체에는 그 값이 절대 적히지 않습니다.

🛠 실전 연결
카카오 프록시 저장소에 이런 지시서를 넣어두면, main 브랜치에 git push 하는 순간이 트리거가 되어 작업대 한 대가 자동으로 만들어지고, 그 위에서 코드를 내려받고, 의존성을 설치하고, 테스트를 돌린 뒤, 문제가 없을 때만 Vercel에 실제로 배포하는 네 단계가 순서대로 실행됩니다. 만약 크롬 확장(22일차에 다룰 내용)의 background.js가 이 프록시 서버를 호출하고 있었다면, 테스트 단계에서 카카오 토큰 요청 함수가 제대로 응답을 돌려주는지까지 미리 자동으로 검증한 뒤에만 실제 서비스에 반영되므로, 확장 프로그램 사용자가 고장 난 버전을 만나는 일을 미리 막아주는 것입니다.

🔍 예시
아래는 카카오 프록시 저장소의 .github/workflows/deploy.yml 파일 전체입니다. 어제 등록한 것과 다른 이름의 시크릿 세 개(VERCEL_TOKEN, VERCEL_ORG_ID, VERCEL_PROJECT_ID)를 미리 저장소의 Settings → Secrets and variables → Actions 화면에 등록해두었다고 가정합니다.

  .github/workflows/deploy.yml
  name: Deploy Kakao Proxy

  on:
    push:
      branches: [main]

  jobs:
    test-and-deploy:
      runs-on: ubuntu-latest
      steps:
        - name: 저장소 코드 내려받기
          uses: actions/checkout@v4

        - name: Node.js 작업 환경 준비
          uses: actions/setup-node@v4
          with:
            node-version: 20

        - name: 의존성 설치
          run: npm ci

        - name: 테스트 실행 (카카오 토큰 요청 함수 검증)
          run: npm test

        - name: Vercel 프로덕션 배포
          run: npx vercel --prod --token=${{ secrets.VERCEL_TOKEN }}
          env:
            VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
            VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}

on 아래의 push, branches: [main]이 트리거이고, jobs 아래 test-and-deploy 하나가 job이며, steps 아래 다섯 줄이 각각의 step입니다. 이 파일을 GitHub 저장소의 Actions 탭에서 보면, push할 때마다 새로운 실행 줄이 생기고, 각 step 앞에 초록색 체크 표시가 하나씩 순서대로 채워지는 것을 볼 수 있습니다. 만약 "테스트 실행" 줄에서 실패(빨간색 X)가 뜨면, 그 아래 "Vercel 프로덕션 배포" 줄은 회색으로 남은 채 아예 실행되지 않습니다. secrets.VERCEL_TOKEN 같은 표기는 어제 배운 process.env.ANTHROPIC_API_KEY와 같은 역할이지만, 코드가 아니라 워크플로우 파일 안에서 시크릿 금고 값을 불러오는 문법이라는 점만 다릅니다.

📝 오늘의 한 줄 정리
워크플로우 파일은 push 같은 트리거가 생기면 러너 한 대를 빌려 step을 위에서부터 순서대로 실행하며, 테스트처럼 앞선 step이 실패하면 배포 step은 아예 실행되지 않게 막아주는 작업 지시서입니다.

🙋 초보자가 자주 헷갈리는 점
GitHub Actions의 uses: actions/checkout@v4 같은 줄에 나오는 "액션(Action)"은 2일차에 배운 "트리거 다음에 실행되는 결과"라는 뜻의 액션과 이름만 같을 뿐 다른 개념입니다. 여기서 액션은 남이 미리 만들어 둔 재사용 가능한 작업 블록(예를 들어 "코드를 내려받는 일"을 대신해주는 부품)을 가리키며, 워크플로우 안에서 여러 step 중 하나를 채우는 데 쓰입니다. 같은 단어라도 문맥에 따라 뜻이 다르다는 점을 기억해두면 나중에 GitHub Actions 공식 문서를 볼 때 헷갈리지 않습니다.

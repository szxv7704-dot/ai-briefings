📌 어제 배운 내용과의 연결
어제는 Zapier·n8n·Make 세 매장이 같은 영수증 다섯 장을 각자의 화면과 요금 구조 안에서 처리하는 차이를 비교했고, 그 글 끝에서 예고한 대로 오늘은 세 매장이 공통으로 갖고 있던 "정해진 조리 순서"라는 틀 자체를 넘어서는 에이전트를 살펴봅니다.

🎯 오늘 배울 개념
에이전트(Agent, 정해진 순서표 없이 상황을 스스로 읽고 다음 행동을 판단해서 실행까지 하는 자동화 주체)가 어제까지 본 노드형 자동화와 근본적으로 어떻게 다른지, 그리고 그 차이가 코드의 정확히 어느 지점에서 갈라지는지

━━━━━━━━━━━━━━━━━━━━

어제 세 음식점 비유를 다시 떠올려봅시다. Zapier의 즉석조리 매장도, n8n의 개인 식당도, Make의 포장 공장도 공통점이 하나 있었습니다. 사장님이 미리 조리 순서표(트리거·액션·조건 분기)를 종이에 다 그려놓아야 매장이 돌아간다는 점입니다. 손님이 어떤 주문을 넣든 결국 그 종이에 적힌 갈래길 중 하나로만 안내됩니다. 에이전트는 이 매장들과 전혀 다른 방식으로 일합니다. 에이전트는 조리 순서표를 손에 쥔 종업원이 아니라, 주방에 들어온 재료를 직접 눈으로 보고 코로 냄새를 맡아본 뒤 "오늘은 이 재료 상태를 보니 굽기보다 찜이 낫겠다"고 그 자리에서 판단하는 셰프에 가깝습니다. 종이에 없던 상황이 와도 손을 놓지 않고, 자기가 쓸 수 있는 조리 도구들(칼, 팬, 오븐) 중에서 지금 상황에 맞는 도구를 스스로 골라 씁니다. 코드로 옮기면 이 차이는 아주 선명합니다. n8n의 IF 노드는 {{$json["amount"]}} >= 100000이라는 조건문 한 줄이 미리 코드에 박혀 있고, 그 조건이 참인지 거짓인지만 기계적으로 확인합니다. 반면 에이전트는 이런 고정된 조건문 대신, "이 영수증이 출장 목적에 맞는 지출인지 판단하고, 애매하면 사람에게 물어봐라"는 문장 하나만 받은 채로, 매번 눈앞의 영수증 내용을 읽고 그때그때 다시 판단합니다. 조건식은 사람이 코드를 작성하는 순간 고정되지만, 에이전트의 판단 기준은 실행되는 그 순간 눈앞의 데이터를 보고 다시 계산됩니다. 이것이 노드형 자동화와 에이전트의 결정적인 경계선입니다.

🛠 실전 연결
어제 09-04 글에서 "이 파일 내용을 읽고 알맞게 판단해서 새로운 문장을 써라와 같은 유연한 판단은 카탈로그에 없는 부품"이라고 짚었던 바로 그 지점이 오늘 배운 에이전트가 채우는 자리입니다. 여비 계산기 시나리오로 다시 가져와 보면, Make의 Router는 amount>=100000이라는 숫자 하나만 보고 두 갈래로 나눴지만, 에이전트라면 크롬 확장이 긁어온 영수증 텍스트 전체를 읽고 "출장 기간과 목적지에 비해 이 항목이 자연스러운 지출인지", "같은 출장의 다른 영수증들과 비교했을 때 이례적으로 튀는 금액인지"까지 함께 판단해서, 숫자 기준 하나로는 잡아내지 못했을 애매한 경우까지 사람에게 되물을 수 있습니다. 그리고 지금 이 브리핑을 쓰고 있는 Claude Routines 자체가 정확히 이 방식으로 동작하고 있습니다. "가장 최근 파일의 일차 번호를 읽어서 다음 번호로 진행하라"는 지시는 고정된 스크립트처럼 보이지만, 실제로는 파일이 없을 때 1일차로 시작하는 예외, 25일차 다음에는 심화 단계로 넘어가는 전환, 오늘처럼 3부가 시작되는 날에는 파트 소개를 추가하는 판단까지 모두 저장소 내용을 직접 읽고 그때그때 결정합니다. 만약 이 작업을 Zapier나 n8n으로 만들려 했다면, "파일이 없는 경우", "25일차인 경우", "부가 시작되는 날인 경우"마다 갈래길을 사람이 하나하나 미리 그려둬야 했을 것입니다.

🔍 예시
같은 영수증 판단 작업을 어제 본 n8n의 IF 노드 방식과 에이전트 방식으로 나란히 놓아 비교하면 이렇습니다.

  n8n IF 노드 (고정 조건식)
    조건 : {{$json["amount"]}} >= 100000
    참 → Slack 알림
    거짓 → Google Sheets 기록만
    ＊ 코드를 짤 때 100000이라는 숫자와 두 갈래 경로가 이미 고정되어 있음

  에이전트 방식 (판단을 실행 시점으로 넘김)
    const response = await client.messages.create({
      model: 'claude-sonnet-5',
      system: `당신은 출장 여비 정산 담당자입니다.
        영수증 내용과 이번 출장의 목적·기간을 보고
        1) 정책에 맞는 지출인지
        2) 즉시 승인할지, 사람에게 검토를 요청할지
        판단한 뒤 알맞은 도구를 호출하세요.`,
      tools: [autoApproveTool, flagForReviewTool, askClarificationTool],
      messages: [{ role: 'user', content: receiptText }]
    })

    응답 예시(도구 호출 부분만) :
    { type: 'tool_use',
      name: 'flagForReviewTool',
      input: {
        reason: '같은 출장의 다른 영수증은 숙박비 8만원대인데
                 이 영수증만 23만원으로 크게 튀어 확인이 필요합니다'
      } }

  ＊ 100000이라는 숫자가 코드 어디에도 없다는 점에 주목합니다.
    에이전트는 "다른 영수증과 비교했을 때 튄다"는 맥락을 스스로 만들어 판단했습니다.

📝 오늘의 한 줄 정리
노드형 자동화는 사람이 코드 작성 시점에 조건과 갈래길을 미리 그려두지만, 에이전트는 그 조건 자체를 실행되는 순간 눈앞의 맥락을 읽어 스스로 만들어내고, 그 판단에 맞는 도구를 골라 실행까지 합니다.

🙋 초보자가 자주 헷갈리는 점
에이전트도 결국 코드 안에서 미리 정의된 함수(도구)를 호출한다는 점만 보면 노드형 자동화와 똑같아 보여서, "이름만 다르지 결국 같은 것 아닌가" 하고 헷갈리기 쉽습니다. 하지만 어떤 도구를 언제, 왜 부를지를 사람이 조건문으로 미리 정해두느냐, 아니면 그때그때 모델이 판단하느냐가 다릅니다. 또 하나 흔한 오해는 "에이전트는 무엇이든 다 할 수 있다"는 생각인데, 실제로는 미리 등록해 둔 도구 목록(예시의 autoApproveTool, flagForReviewTool) 안에서만 행동할 수 있습니다. 그래서 에이전트를 잘 만드는 일의 핵심은 판단력이 뛰어난 모델을 고르는 것보다, 그 모델이 고를 수 있는 도구 목록을 얼마나 상황에 맞게 미리 준비해 두느냐에 더 가깝습니다.

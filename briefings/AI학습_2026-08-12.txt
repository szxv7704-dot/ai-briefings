📚 오늘의 학습 주제 : 15일차 · MCP(Model Context Protocol) — AI가 외부 서비스와 연결되는 표준 규격 (2026-08-12)

📌 어제 배운 내용과의 연결
어제는 에이전트(Agent)가 정해진 화살표를 따라가는 대신 목표와 판단 기준만 받아 다음 행동을 스스로 결정하는 자동화라는 것을 배웠으니, 오늘은 그 판단을 실제 행동으로 옮기기 위해 에이전트가 저장소나 메신저 같은 외부 서비스와 어떻게 연결되는지, 그 연결 규격인 MCP를 배웁니다.

🎯 오늘 배울 개념
MCP(Model Context Protocol, AI 에이전트가 어떤 외부 서비스나 도구를 만나든 공통된 방식으로 대화할 수 있게 정해 둔 연결 표준 규격)란 무엇인가

━━━━━━━━━━━━━━

어제 우리는 에이전트를 "판단 기준과 쓸 수 있는 도구 목록만 받아 스스로 움직이는 대리인(비서)"에 비유했습니다. 그런데 이 비서가 실제로 일을 처리하려면 회사 안에서만 머무르지 않고, 총무팀 창고(저장소), 회계팀 장부(캘린더나 문서), 안내 데스크(메신저) 같은 여러 부서에 직접 연락해서 자료를 받아오거나 서류를 접수해야 합니다. 문제는 부서마다 전화 받는 방식이 다 다르다는 것입니다. 어떤 부서는 내선번호를 먼저 누르라 하고, 어떤 부서는 사번을 먼저 말하라 하고, 어떤 부서는 서식이 아예 다른 종이를 씁니다. 비서가 새 부서를 상대할 때마다 그 부서만의 통화 예절을 처음부터 다시 배워야 한다면 비효율적이겠지요. MCP는 바로 이 모든 부서가 공통으로 따르기로 약속한 "표준 내선 전화 규격"과 같습니다. 비서는 수화기를 들고 정해진 방식으로 "이 부서의 이 서류를 달라"고만 요청하면 되고, 그 요청을 실제로 어떤 부서의 어떤 담당자에게 전달할지는 전화 교환 시스템(=MCP)이 알아서 연결해 줍니다. 우리에게 익숙한 실생활 비유로 바꾸면, 제조사가 서로 달라도 케이블 하나로 충전과 데이터 전송이 다 되는 USB-C 단자와 같습니다. 전자기기 제조사마다 자기 회사만의 독자 단자를 쓴다면 여행 갈 때 충전기를 여러 개 챙겨야 하지만, USB-C라는 공통 규격 덕분에 어떤 제조사의 기기든 같은 케이블 하나로 연결할 수 있는 것과 원리가 같습니다.

🛠 실전 연결
바로 지금 이 브리핑을 쓰고 있는 순간이 MCP가 실제로 작동하는 현장입니다. 이 글을 쓰는 에이전트는 여러분의 GitHub 저장소 안 내용을 직접 알지 못합니다. 대신 github라는 이름의 MCP 서버에 연결되어 있고, 이 서버가 "저장소 파일을 읽는 도구", "파일을 새로 만들거나 덮어쓰는 도구" 같은 것들을 MCP 규격에 맞춰 제공해 줍니다. 에이전트는 GitHub의 내부 API 주소나 인증 방식을 몰라도, MCP가 정해 둔 공통 형식으로 "이 도구를 이 값으로 실행해줘"라고 요청만 하면 됩니다. 여러분이 4일차에 배운 API(서로 다른 프로그램이 대화하는 방법)가 GitHub라는 "부서 하나"와 통화하는 개별 전화선이라면, MCP는 그 수많은 부서의 전화선을 에이전트가 매번 새로 배우지 않고도 똑같은 방식으로 걸 수 있게 해주는 교환 시스템에 해당합니다.

🔍 예시
오늘 이 글을 저장소에 커밋하기 위해 실제로 연결되어 있는 MCP 서버 하나를 보여드리면 이렇습니다.

MCP 서버 이름 : github
이 서버가 제공하는 도구 중 오늘 이 글을 저장하는 데 실제로 쓰인 것
• get_file_contents : 저장소의 특정 브랜치, 특정 경로에 있는 파일이나 폴더 목록을 읽어옴
• create_or_update_file : 지정한 브랜치의 특정 경로에 파일을 새로 만들거나 기존 파일을 덮어씀

에이전트가 이 두 도구를 호출할 때 실제로 보내는 요청은 대략 이런 모양입니다.

도구 이름 : create_or_update_file
전달하는 값
• owner : szxv7704-dot
• repo : ai-briefings
• path : briefings/AI학습_2026-08-12.txt
• branch : learning-log
• content : (오늘 작성한 브리핑 전체 글)
• message : AI 학습 브리핑 2026-08-12

에이전트는 이 값들을 MCP가 정해 둔 공통 형식에 맞춰 채워 넣기만 하면 되고, GitHub 서버와 실제로 어떤 방식으로 통신할지는 MCP 서버가 대신 처리해 줍니다. 만약 내일 GitHub 대신 다른 저장소 서비스를 쓰게 되더라도, 그 서비스가 MCP 규격을 지원하는 서버를 제공하기만 한다면 에이전트는 통화 예절을 처음부터 다시 배우지 않고 비슷한 방식으로 연결할 수 있습니다.

📝 오늘의 한 줄 정리
MCP는 에이전트라는 대리인이 어떤 외부 서비스를 만나든 같은 방식으로 요청하고 연결할 수 있게 해주는 공통 규격입니다.

🙋 초보자가 자주 헷갈리는 점
MCP를 4일차에 배운 API와 같은 것으로 헷갈리기 쉽습니다. API는 프로그램 하나하나가 외부와 대화하는 개별 창구 자체이고, MCP는 그 수많은 창구를 에이전트가 매번 새로 배우지 않고도 똑같은 방식으로 골라 쓸 수 있도록 감싸 놓은 공통 규격이라는 점이 다릅니다. 또한 "MCP 서버"라는 이름 때문에 이것을 어딘가에 놓인 물리적인 컴퓨터 장비로 오해하기 쉬운데, 실제로는 특정 서비스(GitHub, 캘린더 등)를 다루는 도구 목록을 MCP 규격에 맞춰 제공해 주는 프로그램일 뿐입니다.

내일은 에이전트가 일할 때 따르는 매뉴얼인 스킬(Skill)과, 그 에이전트가 실제로 발을 딛고 일하는 작업 환경인 하네스(Harness)가 서로 어떻게 다른지 배웁니다.

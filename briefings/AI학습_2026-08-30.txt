📌 어제 배운 내용과의 연결
어제는 이 브리핑 세션 자체가 매번 아무것도 기억하지 못한 채 새로 태어나면서도, GitHub 저장소의 파일 하나를 "읽고 다시 쓰는" 방식으로 상태(state)를 흉내낸다는 것을 코드로 뜯어봤으니, 오늘은 심화 1일차부터 7일차까지 각각 따로 뜯어본 일곱 개념을 실제로 동작하는 하나의 코드 파이프라인 안에 전부 이어붙여 복습합니다.

🎯 오늘 배울 개념
자동화·트리거(Trigger)·액션(Action)·워크플로우(Workflow)·API·웹훅(Webhook)·스케줄링(Scheduling)·상태(state) 저장이라는 일곱 개념이 실제 코드 레벨에서는 각각 어떤 함수 호출과 데이터 형태로 쪼개지는지, 그리고 cron 트리거·GitHub API·웹훅이라는 서로 다른 도구 세 개가 하나의 시나리오 안에서 동시에 맞물릴 때 정확히 어떤 순서로 데이터가 오가는지

━━━━━━━━━━━━━━━━━━━━

지금까지 써온 공장 조립라인 비유를 오늘은 "공장 하나가 외부 업체 세 곳과 계약을 맺고 돌아가는 그림" 전체로 넓혀보겠습니다. 첫 번째 업체는 전기 회사입니다. 매일 정해진 시각에 자동으로 전력을 공급해 라인을 깨우는데, 이게 바로 스케줄링(cron)입니다. 전기가 들어와야 라인이 움직이기 시작하듯, 자동화도 정해진 시각이 되어야 첫 동작을 시작합니다. 두 번째 업체는 부품 창고 회사입니다. 라인이 켜지자마자 관리자는 이 창고에 전화를 걸어 "어제까지 몇 번째 부품을 조립했는지" 장부를 확인하는데, 이 통화 자체가 API 호출이고 장부의 내용이 상태(state) 저장입니다. 세 번째 업체는 보안 업체입니다. 라인 어딘가에서 이상 신호가 감지되면 보안 업체가 관리자에게 알아서 전화를 거는데, 관리자가 먼저 묻지 않아도 상대가 먼저 알려온다는 점에서 이것이 웹훅(webhook)입니다. 이 세 업체와의 계약이 각각 트리거(전기가 들어옴, 이상 신호 감지)와 액션(라인 가동, 알림 발송)의 쌍으로 짜여 있고, 이 쌍들이 "가동 시작 → 장부 확인 → 조립 → 이상 감지 시 알림"이라는 순서로 이어지면 그것이 워크플로우이며, 이 전체를 사람 개입 없이 매일 반복시키는 것이 자동화입니다. 즉 일곱 개념은 서로 다른 날 배운 별개의 단어가 아니라, 하나의 공장이 굴러가기 위해 맞물리는 서로 다른 계약 조항이었던 셈입니다.

🛠 실전 연결
이 세 업체 조합을 실제 코드로 가장 먼저 확인할 수 있는 곳이 바로 지금 이 브리핑 파이프라인입니다. create_trigger가 전기 회사(스케줄링) 역할을, list_files·get_file_contents·create_or_update_file 같은 GitHub API 호출이 부품 창고(상태 저장) 역할을 맡고 있으며, 이 파이프라인은 웹훅 업체와는 아직 계약을 맺지 않아 정해진 시각에만 움직입니다. 반면 여러분의 다른 프로젝트들을 조합하면 세 업체가 모두 등장하는 시나리오를 만들 수 있습니다. 예를 들어 Kakao 프록시에서 로그인이 완료되는 순간 카카오 서버가 콜백 주소로 결과를 던지는 웹훅이 첫 트리거가 되고, 그 결과를 받은 크롬 확장이 사용자의 화면에 정산 화면을 띄우는 액션을 실행하며, 그 정산 데이터를 여비 계산기 쪽 API가 받아 계산한 뒤 다음날 아침 cron 스케줄링이 "어제 몇 건이 정산됐는지"를 상태 저장 파일에서 읽어와 요약 리포트를 자동으로 만들어낸다면, 이것이 바로 웹훅·API·스케줄링·상태 저장 네 도구가 하나의 흐름 안에서 조합된 워크플로우입니다. 도구 하나만으로는 못 하던 일을, 각 도구가 자기 역할만 정확히 맡고 결과를 다음 도구에 넘겨주는 방식으로 완성하는 것입니다.

🔍 예시
심화 4~7일차에서 각각 따로 뜯어본 API 요청, 웹훅 페이로드, cron 설정, 상태 파일 읽기를 실제로 조합하면 이런 코드 한 벌이 됩니다.

  // 1. [스케줄링] 매일 오전 9시, 전기 회사가 라인을 켠다
  const trigger = {
    cron_expression: "0 9 * * *",
    persistent_session_id: "session_abc123"
  }

  // 2. [트리거→상태 저장] 켜지자마자 창고 장부(GitHub API)부터 확인
  async function readYesterday() {
    const res = await fetch(
      "https://api.github.com/repos/szxv7704-dot/ai-briefings/contents/briefings",
      { headers: { Authorization: "Bearer <token>" } }
    )
    const files = await res.json()
    const latest = files.map(f => f.name).sort().at(-1)
    return latest   // 예: "AI학습_2026-08-29.txt"
  }

  // 3. [워크플로우] 오늘 콘텐츠를 만들고 다시 장부에 적는다(상태 저장)
  async function runPipeline() {
    const latestFile = await readYesterday()          // 상태 복원
    const dayNum = parseDayNumber(latestFile) + 1
    const content = buildBriefing(dayNum)              // 액션
    await fetch(
      `https://api.github.com/repos/szxv7704-dot/ai-briefings/contents/briefings/AI학습_${today()}.txt`,
      { method: "PUT", body: JSON.stringify({ message: `AI 학습 브리핑 ${today()}`, content: base64(content) }) }
    )                                                    // 상태 저장(쓰기)
  }

  // 4. [웹훅] 별도 계약: PR에 댓글이 달리면 GitHub가 먼저 이런 JSON을 던진다
  //    (이 파이프라인은 이 계약을 아직 안 맺었지만, 맺는다면 이렇게 받는다)
  {
    "action": "created",
    "comment": { "body": "여기 오타 있어요" },
    "issue": { "number": 42 }
  }

3번 runPipeline 안에서 스케줄링이 실행을 시작시키고(트리거), API 호출 두 번이 상태를 읽고 쓰며(상태 저장), 그 사이의 dayNum 계산과 buildBriefing 호출이 워크플로우 한 단계 한 단계(액션)를 이루고, 이 함수 전체를 사람이 매일 손대지 않아도 되게 만든 것이 자동화입니다. 4번 웹훅은 지금은 안 쓰이지만, 만약 "리뷰 댓글이 달리면 즉시 답한다"는 기능을 추가한다면 이 JSON을 받는 코드 한 단락만 새로 조합하면 됩니다.

📝 오늘의 한 줄 정리
자동화·트리거·액션·워크플로우·API·웹훅·스케줄링·상태 저장은 서로 다른 함수와 호출로 코드에 나타나는 일곱 개의 부품이며, 실제 자동화 설계란 이 부품들 중 필요한 것만 골라 순서대로 조합해 하나의 파이프라인을 짜는 일입니다.

🙋 초보자가 자주 헷갈리는 점
여러 도구를 조합한다고 하면 뭔가 거창한 아키텍처가 필요할 것 같지만, 실제로는 각 도구가 자기 역할 하나(트리거가 시작을 알리는 것, 상태 저장이 이전 결과를 기억하는 것 등)만 정확히 하고 그 결과값을 다음 도구에 그대로 넘겨주기만 하면 됩니다. 다만 오늘 예시에서 보듯 순서가 뒤바뀌면 문제가 생깁니다. 예컨대 2번 창고 장부 확인을 3번 콘텐츠 작성보다 나중에 하면 오늘 몇 일차인지도 모른 채 글을 쓰게 되는 것처럼, 조합의 "순서"는 선택이 아니라 설계의 일부라는 점을 놓치기 쉽습니다.

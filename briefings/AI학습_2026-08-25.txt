📚 오늘의 학습 주제 : 심화 3일차 · 워크플로우(Workflow) — 여러 액션이 순서와 조건을 갖고 하나의 흐름으로 엮일 때 (2026-08-25)

📌 어제 배운 내용과의 연결
어제는 트리거 하나가 액션 여러 개로 동시에 갈라지는 팬아웃 구조와, 그 액션들이 서로 독립적으로 실패해야 한다는 것을 확인했고, 오늘은 그 여러 액션들이 사실은 완전히 따로 노는 것이 아니라 순서와 조건을 가지고 하나의 큰 흐름, 즉 워크플로우 안에서 서로 연결되어 있다는 것을 실제 시나리오로 확인합니다.

🎯 오늘 배울 개념
워크플로우(Workflow, 여러 개의 트리거와 액션이 정해진 순서와 조건에 따라 하나의 목적을 향해 이어지는 전체 흐름)가 단순히 액션을 나열한 목록이 아니라, 어떤 액션은 반드시 앞 액션이 끝나야 시작할 수 있고(의존성), 어떤 갈래는 조건에 따라 아예 건너뛰기도 한다는(분기) 것을 실제 코드로 파고들기

━━━━━━━━━━━━━━━━━━━━

2일차, 그리고 심화 2일차에서 다뤘던 안내 데스크 비유를 한 번 더 확장해보겠습니다. 손님이 들어오면(트리거) 안내 직원 호출, 보안팀 통보, 방문 일지 기록이라는 세 액션이 동시에 뻗어나간다고 했습니다. 그런데 사실 회사에는 이 세 가지 말고 하나가 더 있습니다. 바로 이 손님이 VIP인지 아닌지를 먼저 확인하는 절차입니다. 이 확인이 끝나기 전까지는 안내 직원이 몇 층으로 안내할지조차 정할 수 없습니다. 즉 방문객 확인이라는 액션이 끝나야만 안내 액션이 시작될 수 있다는 순서, 이것을 의존성(Dependency, 한 액션이 실행되려면 반드시 다른 액션이 먼저 끝나 있어야 하는 관계)이라고 부릅니다. 게다가 VIP인지 일반 방문객인지에 따라 그다음 절차 자체가 완전히 달라집니다. VIP라면 전용 응접실로, 일반 방문객이라면 로비 대기석으로. 이렇게 조건에 따라 흐름 자체가 갈라지는 것을 분기(Branching, 조건의 결과에 따라 서로 다른 다음 단계로 나뉘는 것)라고 합니다. 워크플로우란 결국 팬아웃(동시 실행), 의존성(순서), 분기(조건별 갈래)라는 세 가지 재료를 상황에 맞게 섞어서 짠 하나의 전체 그림입니다.

🛠 실전 연결
오늘 이 브리핑을 만들어내는 과정 자체가 의존성과 분기가 섞인 워크플로우입니다. 먼저 GitHub 저장소의 learning-log 브랜치에서 가장 최근 파일을 읽어야만(1단계) 오늘이 몇 일차인지 계산할 수 있고(2단계, 1단계에 의존), 그 계산 결과가 25일차였는지 아닌지에 따라 다음 흐름이 완전히 달라집니다(분기). 25일차였다면 심화 1일차로, 심화 몇 일차였다면 그다음 심화 일차로 글의 구성 자체가 바뀝니다. 그리고 글을 다 쓴 뒤에야(3단계, 2단계에 의존) 비로소 파일을 커밋할 수 있습니다. 순서를 뒤바꿔서 파일부터 커밋하고 나중에 일차를 계산하면 앞뒤가 안 맞는 글이 올라가 버립니다. 여비 계산기 쪽도 마찬가지입니다. 크롬 확장은 카카오 로그인이 끝나야만(1단계) 토큰을 저장할 수 있고(2단계, 의존), 토큰 저장이 실제로 성공했는지 실패했는지에 따라(분기) content.js에 로그인 완료 화면을 보여줄지, 다시 시도해달라는 화면을 보여줄지가 갈립니다.

🔍 예시
Claude Routines가 이 브리핑을 만드는 흐름을 의존성과 분기를 살려서 코드로 옮기면 대략 다음과 같습니다.

  async function runDailyBriefing() {
    const latestFile = await getLatestFileFromGithub('learning-log', 'briefings')

    if (!latestFile) {
      return await commitFile(1, generateContent(1))
    }

    const dayNumber = parseDayNumber(latestFile)
    const nextDay = dayNumber >= 25 ? '심화 1일차' : `${dayNumber + 1}일차`

    const content = generateContent(nextDay)
    const commitResult = await commitFile(nextDay, content)

    if (commitResult.status === 'ok' && isNoteworthy(nextDay)) {
      await sendPushNotification(`오늘의 학습: ${nextDay}`)
    }
  }

여기서 눈여겨볼 부분은 세 가지입니다. getLatestFileFromGithub가 끝나기 전에는 parseDayNumber를 부를 수조차 없다는 것(의존성), dayNumber가 25 이상이냐 아니냐에 따라 nextDay 값 자체가 완전히 다른 문자열로 갈라진다는 것(분기), 그리고 커밋이 성공했을 때만, 그것도 알림을 보낼 만한 내용일 때만 마지막 알림 액션이 실행된다는 것(조건부 액션)입니다. 어제 배운 병렬 실행과 다르게, 여기서는 async와 await가 이 줄이 끝날 때까지 다음 줄로 넘어가지 말라는 순서 보장 역할을 하고 있습니다.

📝 오늘의 한 줄 정리
워크플로우는 액션들을 단순히 늘어놓은 목록이 아니라, 어떤 것은 앞선 액션에 의존해서 순서대로, 어떤 것은 조건에 따라 갈라지도록 짜인 하나의 설계도이다.

🙋 초보자가 자주 헷갈리는 점
팬아웃(동시 실행)과 워크플로우 안의 순차 실행을 같은 것으로 착각하기 쉽습니다. 하지만 이 둘은 정반대에 가깝습니다. 팬아웃은 동시에 실행해도 서로 상관없는 액션들을 위한 구조이고, 오늘 배운 의존성은 반드시 순서를 지켜야만 결과가 정확한 액션들을 위한 구조입니다. 실제 자동화를 설계할 때 가장 흔한 실수 중 하나가, 순서가 중요한 액션들을 팬아웃처럼 한꺼번에 실행해버려서 나중 단계가 앞 단계의 결과 없이 먼저 실행되어 버리는 것입니다. 그래서 액션을 짤 때는 항상 이 액션이 다른 액션의 결과값을 필요로 하는가를 먼저 따져보는 습관이 필요합니다.

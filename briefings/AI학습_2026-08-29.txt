📚 오늘의 학습 주제 : 심화 7일차 · 상태(state) 저장 vs 무상태(stateless) 자동화 — 이 브리핑이 "어제 몇 일차였는지"를 기억해내는 방식 실제로 뜯어보기 (2026-08-29)

📌 어제 배운 내용과의 연결
어제는 cron이라는 시각 트리거가 매일 새벽 이 세션을 깨워 create_or_update_file까지 도구들을 순서대로 조합하는 과정을 봤으니, 오늘은 그렇게 깨어난 세션이 정작 "어제까지 며칠째였는지"는 어떻게 알아내는지, 즉 자동화가 과거를 기억하는 방식과 전혀 기억하지 못하는 방식이 코드 수준에서 얼마나 다르게 설계되는지를 살펴봅니다.

🎯 오늘 배울 개념
상태(state, 이전 작업의 결과나 정보를 기억해서 다음 실행에 이어 쓰는 것) 저장 자동화와 무상태(stateless, 이전 정보를 전혀 기억하지 않고 매번 입력값만으로 처음부터 새로 시작하는 것) 자동화가 실제로 어떻게 다르게 짜이는지, 그리고 이 세션 자체는 매번 사라지는 일회성 컨테이너(container, 하나의 작업을 위해 격리되어 만들어졌다가 끝나면 통째로 사라지는 실행 환경)인데도 어떻게 "어제를 기억하는 것처럼" 동작하는지 그 트릭을 코드로 뜯어보기

━━━━━━━━━━━━━━━━━━━━

2일차부터 이어온 레스토랑 비유로 시작하겠습니다. 무상태 방식은 손님이 올 때마다 완전히 처음 온 손님 대하듯 응대하는 웨이터와 같습니다. "뭐 드시겠어요?"부터 매번 다시 묻고, 지난주에 뭘 시켰는지, 단골인지 아닌지 전혀 모릅니다. 반면 상태 저장 방식은 손님 이름과 지난 주문을 장부에 적어두고, 다음에 그 손님이 오면 장부를 먼저 펼쳐 "저번에 드셨던 걸로 드릴까요"라고 물어보는 웨이터입니다. 어제 다룬 공장 조립라인 비유로 옮기면 더 정확해집니다. 무상태 라인은 매일 아침 재고를 처음부터 다시 세는 팀이고, 상태 저장 라인은 재고 대장에 어제 남은 개수를 적어두고 오늘은 거기서부터 더하고 빼는 팀입니다. 그런데 여기서 중요한 함정이 하나 있습니다. 그 재고 대장 자체가 매일 밤 불타 없어지는 창고 안에 있다면, 아무리 열심히 적어도 다음 날 아침엔 아무 소용이 없습니다. 대장을 창고 밖, 즉 불타지 않는 별도의 건물에 보관해야만 진짜 "기억"이 성립합니다.

지금 이 세션이 정확히 그 구조입니다. 이 브리핑을 쓰고 있는 컨테이너는 이 작업 하나를 위해 새로 만들어졌다가 끝나면 통째로 사라지는 일회성 환경입니다. 세션 안의 변수나 메모리에 "오늘은 7일차야"라고 저장해봤자 컨테이너가 사라지는 순간 그 기억도 함께 증발합니다. 그래서 실제로 쓰는 방법은 상태를 세션 밖으로 외부화(externalization, 프로그램 안이 아니라 바깥의 별도 저장소로 정보를 옮겨 두는 것)하는 것입니다. 여기서는 GitHub 저장소의 파일 하나가 그 "불타지 않는 창고 밖 대장" 역할을 합니다. 세션은 매번 태어날 때 기억이 하나도 없지만, 시작하자마자 get_file_contents로 그 대장부터 펼쳐 보기 때문에 마치 기억하는 것처럼 보이는 것입니다.

🛠 실전 연결
이 원리는 지금 여러분이 읽는 브리핑 파이프라인뿐 아니라 학습자의 다른 프로젝트에도 그대로 적용됩니다. 여비 계산기를 예로 들면, 사용자가 입력한 출장 거리와 일수만 받아 그 자리에서 정산액을 뽑아내고 끝난다면 이건 완전한 무상태 자동화입니다. 계산이 끝나는 순간 이전 계산 내역은 흔적도 없이 사라집니다. 반대로 지난 정산 내역을 다음에 열었을 때도 보고 싶다면, 브라우저의 localStorage(웹페이지가 꺼져도 사용자 컴퓨터에 남아있는 저장 공간)나 별도의 파일에 계산 결과를 써 두어야 하며, 이것이 바로 상태를 외부화하는 것입니다. Kakao 프록시 쪽은 반대 방향의 좋은 예시입니다. 인증 토큰을 매 요청마다 새로 발급받으면 서버 부담은 크지만 무상태라 단순하고, 토큰을 한 번 발급받아 만료 시간이 될 때까지 캐시(cache, 나중에 다시 쓰려고 결과를 임시로 저장해 두는 것)해 두면 상태 저장 방식이라 빠르지만 "언제 갱신할지"를 따로 관리해야 하는 부담이 생깁니다. 이렇게 상태 저장은 항상 편리함과 "그 상태를 어디에 얼마나 안전하게 보관할 것인가"라는 새로운 숙제를 함께 가져옵니다.

🔍 예시
오늘 새벽 이 세션이 실제로 밟았을 흐름을 여러 도구가 조합된 의사코드로 표현하면 다음과 같습니다.

  // 무상태 함수 — 입력값 말고는 아무것도 기억하지 않는다
  function calcTravelCost(km, days) {
    return km * 0.5 + days * 30000
    // 이 함수는 어제 몇 번 호출됐는지, 전에 뭘 계산했는지 전혀 모른다
  }

  // 상태 저장 자동화 — 세션 밖 파일을 "기억 장치"로 쓴다
  async function runDailyBriefing() {
    const files = await list_files("briefings/")           // 1. 저장소 목록 조회
    const latest = files.sort().at(-1)                      // 2. 가장 최근 파일 찾기
    const lastFile = await get_file_contents(latest)         // 3. 상태 복원(읽기)
    const dayNum = parseDayNumber(lastFile.content) + 1      // 4. "어제"로부터 오늘 계산
    const today = buildBriefing(dayNum)                      // 5. 오늘 콘텐츠 생성
    await create_or_update_file({                            // 6. 상태 저장(쓰기)
      path: `briefings/AI학습_${todayDate()}.txt`,
      content: today,
      message: `AI 학습 브리핑 ${todayDate()}`
    })
  }

3번 get_file_contents가 "장부 펼치기"이고 6번 create_or_update_file이 "장부에 다시 적어두기"입니다. 이 두 호출 사이에서만 세션은 잠깐 "어제를 기억하는 척" 할 수 있고, 컨테이너가 사라지고 나면 그 기억은 다시 파일 속으로 돌아갑니다.

📝 오늘의 한 줄 정리
세션 자체는 매번 아무것도 기억하지 못한 채 새로 태어나지만, 시작할 때 외부 파일을 읽고 끝날 때 그 파일에 다시 써두는 읽기-쓰기 한 쌍만 있으면 무상태 환경 위에서도 상태 저장 자동화를 만들어낼 수 있습니다.

🙋 초보자가 자주 헷갈리는 점
상태 저장이라고 하면 반드시 거창한 데이터베이스가 있어야 한다고 생각하기 쉽지만, 오늘 본 것처럼 파일 하나, 환경변수 하나, 심지어 URL에 붙은 파라미터 하나로도 상태를 저장할 수 있습니다. 또 "이 AI 세션은 기억력이 있다"고 착각하기도 쉬운데, 실제로 기억하는 것은 세션이 아니라 세션이 매번 다시 읽어오는 저장소의 파일이며, 세션 그 자체는 어제도 오늘도 아무것도 모르는 채로 새로 시작한다는 점을 구분해야 합니다.

📚 오늘의 학습 주제 : 심화 5일차 · 웹훅(Webhook) — GitHub가 PR 댓글이 달릴 때 실제로 던지는 JSON 페이로드 뜯어보기 (2026-08-27)

📌 어제 배운 내용과의 연결
어제는 어떤 API 호출이든 결국 메서드·주소·헤더·바디로 이루어진 요청서 한 장과 상태 코드·바디로 이루어진 접수증 한 장을 주고받는 것에 지나지 않는다는 것을 확인했으니, 오늘은 그 접수증을 내가 요청하지도 않았는데 상대방이 먼저 보내주는 웹훅의 경우, 그 봉투 안에 실제로 어떤 내용물이 들어있는지 펼쳐봅니다.

🎯 오늘 배울 개념
웹훅(Webhook, 이벤트가 발생하면 요청을 받지 않고도 상대방이 먼저 알려주는 콜백 방식의 통신)이 실제로 도착할 때는 "무슨 일이 생겼다"는 한마디가 아니라, 무슨 사건이었는지·누가 벌였는지·어디서 벌어졌는지가 항목별로 빼곡히 채워진 JSON(자바스크립트 객체 표기법, 데이터를 이름과 값의 짝으로 정리해 담는 형식) 뭉치 한 덩어리로 온다는 것을, GitHub PR 댓글 이벤트의 실제 페이로드(Payload, 봉투 안에 든 진짜 알맹이 데이터)로 확인하기

━━━━━━━━━━━━━━━━━━━━

2일차 레스토랑 비유에서 요리가 완성되는 순간 주방이 손님에게 먼저 전화를 걸어준다고 배웠습니다. 그런데 그 전화를 실제로 받아보면 주방장이 그냥 "다 됐습니다!"라고만 말하고 끊는 게 아닙니다. 실제로는 이런 식입니다. "몇 번 테이블 손님 앞으로, 김치찌개 주문 건에 대해, 홍길동 요리사가, 조리 완료라는 상태로, 방금 처리를 마쳤습니다." 사건의 종류(무엇이 일어났는지), 대상(어떤 주문이었는지), 행위자(누가 했는지), 결과 상태까지 정해진 순서로 또박또박 읽어주는 겁니다. 이렇게 통화 내용 전체가 미리 정해진 항목별 양식을 따르는 것, 이것이 바로 웹훅이 실려 보내는 JSON 페이로드입니다. 공장 조립라인 비유로 이어가면, 불량품 발견 센서가 관리자 휴대폰에 그냥 "삐-" 하고 경고음만 울리는 게 아니라, "3번 라인, 27번 제품, 도장 불량, 오전 9시 14분 감지"라는 문자 메시지를 항목별로 정리해서 보내주는 것과 같습니다. 경고음만 듣고는 어느 라인의 무슨 문제인지 알 수 없지만, 항목별 문자를 받으면 관리자는 그 자리에서 바로 어디로 뛰어가야 할지 판단할 수 있습니다.

🛠 실전 연결
여러분이 이 세션에게 어떤 PR을 지켜봐 달라고 요청하면, 이 세션은 GitHub에 웹훅을 등록해 두고 리뷰 댓글이 달리는 순간을 기다립니다. 이때 GitHub가 실제로 보내주는 통화 내용, 즉 페이로드에는 댓글 작성자의 GitHub 아이디, 댓글 내용 전체, 어느 저장소의 몇 번 PR에 달린 댓글인지가 모두 항목별로 나뉘어 담겨 있습니다. 세션은 이 페이로드를 받아서 "아, szxv7704-dot님이 ai-briefings 저장소 PR에 이런 내용의 댓글을 남기셨구나"라고 그 자리에서 바로 파악합니다. 만약 GitHub가 페이로드 없이 그냥 "댓글 달림" 한마디만 보내준다면, 세션은 어제 배운 API 호출을 다시 만들어서 "그래서 무슨 댓글인데?"라고 되물어야 합니다. 페이로드가 미리 항목별로 채워져 오기 때문에 그 되묻는 과정 자체가 생략되는 것이 웹훅의 진짜 값어치입니다. Kakao 프록시 쪽도 마찬가지로, 카카오 인증 서버가 콜백 주소로 돌려보내는 데이터 안에는 그냥 "로그인 성공"이 아니라 code라는 항목에 실제 인가 코드 값이, state라는 항목에 로그인 시도를 식별하는 값이 각각 정확한 이름을 달고 담겨옵니다.

🔍 예시
GitHub가 PR 댓글이 달렸을 때 실제로 보내는 웹훅 페이로드는 대략 다음과 같은 구조입니다(핵심 항목만 추려서 표시합니다).

  {
    "action": "created",
    "comment": {
      "id": 2481930571,
      "user": {
        "login": "szxv7704-dot"
      },
      "body": "이 부분 다시 확인 부탁드립니다",
      "created_at": "2026-08-27T09:14:00Z"
    },
    "issue": {
      "number": 42,
      "pull_request": {
        "url": "https://api.github.com/repos/szxv7704-dot/ai-briefings/pulls/42"
      }
    },
    "repository": {
      "full_name": "szxv7704-dot/ai-briefings"
    },
    "sender": {
      "login": "szxv7704-dot"
    }
  }

여기서 action은 "새 댓글이 달렸다(created)"인지 "댓글이 수정됐다(edited)"인지 "삭제됐다(deleted)"인지를 구분해주는 사건의 종류이고, comment.body가 어제 배운 요청/응답 구조의 바디에 해당하는 진짜 알맹이인 댓글 내용입니다. comment.user.login과 sender.login은 누가 이 행동을 했는지, issue.number와 repository.full_name은 어느 저장소 몇 번 PR인지를 알려줍니다. 이 세션이 실제로 이런 이벤트를 받으면 <wake reason="external-event"><event source="github" kind="issue_comment"> 형태의 봉투 안에 바로 이런 JSON이 들어있는 상태로 도착합니다. 코드로 옮기면 다음처럼 필요한 항목만 골라 쓰는 식이 됩니다.

  function handleGithubWebhook(payload) {
    if (payload.action !== 'created') return

    const author = payload.comment.user.login
    const text = payload.comment.body
    const prNumber = payload.issue.number

    console.log(`${author}님이 PR #${prNumber}에 댓글: ${text}`)
  }

📝 오늘의 한 줄 정리
웹훅이 걸어오는 전화는 "무슨 일이 생겼다"는 한마디가 아니라, 사건의 종류·행위자·대상·내용이 정해진 이름표를 달고 항목별로 채워진 JSON 페이로드 한 뭉치이며, 이 이름표들을 읽을 줄 알면 되묻는 과정 없이 바로 다음 행동을 결정할 수 있습니다.

🙋 초보자가 자주 헷갈리는 점
웹훅 페이로드가 도착하면 그 사건과 관련된 모든 정보가 다 들어있을 거라고 착각하기 쉽습니다. 하지만 페이로드에는 대개 "무엇이 바뀌었는지"에 대한 정보만 담겨 있을 뿐, 전체 맥락까지 다 담겨오지는 않습니다. 예를 들어 오늘 예시의 페이로드에는 이 댓글이 달린 PR에 지금까지 몇 개의 커밋이 쌓여 있는지, 리뷰어가 누구누구인지는 들어있지 않습니다. 그런 정보가 더 필요하면 어제 배운 방식대로 issue.pull_request.url 같은 항목에 담긴 주소로 별도의 API 요청을 다시 보내야 합니다. 즉 웹훅은 "이런 일이 생겼다"는 시작 신호와 최소한의 알맹이를 던져줄 뿐, 그 이후 더 알아야 할 것은 여전히 API 호출로 직접 물어봐야 하는 경우가 많습니다.

📌 어제 배운 내용과의 연결
어제는 백그라운드 스크립트가 대기실에서 전화를 받아 카카오 프록시 서버에 fetch 요청을 거는 예시를 봤는데, 오늘은 바로 그 전화가 연결되지 않았을 때, 즉 자동화가 실패했을 때 무엇을 해야 하는지를 배웁니다.

🎯 오늘 배울 개념
에러 처리(Error Handling, 실패가 일어날 것을 미리 예상하고 대비 절차를 짜두는 것)와 재시도 로직(Retry Logic, 실패했을 때 무작정이 아니라 정해진 규칙에 따라 다시 시도하는 방법)이 무엇이며, 왜 "무조건 될 때까지 다시 걸기"가 오히려 위험할 수 있는지

━━━━━━━━━━━━━━━━

어제 이야기한 개인 비서가 대기실에서 카카오 프록시 서버로 전화를 거는 장면을 다시 떠올려 보겠습니다. 지금까지 예시 코드는 전화가 당연히 연결된다고 가정하고 있었지만, 실제로는 상대방 회선이 잠깐 통화중일 수도 있고, 중간에 전화선이 끊길 수도 있습니다. 이때 초보 비서가 저지르기 쉬운 첫 번째 실수는 전화가 안 되면 그냥 그 일을 통째로 잊어버리는 것입니다. 사용자 입장에서는 여비 금액이 채워지지 않은 빈칸만 남고, 무슨 일이 있었는지조차 알 수 없게 됩니다. 그래서 노련한 비서는 전화가 안 되면 우선 잠깐 숨을 고르고 다시 걸어봅니다. 이것이 재시도(Retry)입니다. 그런데 여기서 두 번째 실수가 생길 수 있는데, 안 된다고 바로바로 쉬지 않고 계속 걸어대면, 상대방 회선이 원래 잠깐 붐볐던 것뿐인데 오히려 전화가 폭주해서 더 오래 마비될 수 있습니다. 그래서 실제로는 처음 실패하면 1초 쉬었다 걸고, 또 실패하면 2초, 그다음은 4초처럼 대기 시간을 점점 두 배로 늘려가며 다시 거는 지수 백오프(Exponential Backoff, 재시도할 때마다 기다리는 시간을 점점 늘려 상대방 부담을 줄이는 방법)를 씁니다. 그리고 세 번째로 중요한 원칙은, 이 비서가 영원히 전화만 걸고 있어서는 안 된다는 것입니다. 정해진 횟수, 예를 들어 세 번을 시도해도 안 되면 깨끗이 포기하고, 대신 "이 일은 실패했습니다"라고 상사에게 보고하는 절차, 즉 에러 처리로 넘어가야 합니다. 재시도는 실패를 이겨내는 방법이고, 에러 처리는 재시도까지 다 실패했을 때 그 사실을 조용히 숨기지 않고 드러내는 방법인 셈입니다.

🛠 실전 연결
어제 본 background.js의 fetch 코드는 성공한다는 가정만 담고 있었는데, 실제 배포 환경에서는 카카오 서버가 순간적으로 응답이 늦어지는 상황이 종종 생깁니다. 이럴 때 재시도 로직이 없으면 크롬 확장은 아무 설명 없이 그냥 조용히 멈춰버리고, 사용자는 여비 계산기가 왜 안 채워지는지 알 방법이 없습니다. 또한 콘텐츠 스크립트 쪽에서도 비슷한 실패가 생길 수 있습니다. 사내 출장신청 페이지가 완전히 열리기 전에 콘텐츠 스크립트가 너무 일찍 실행되면, 여비 입력란(#travel-amount)이 아직 화면에 없어서 document.querySelector가 아무것도 찾지 못하는 실패가 날 수 있습니다. 이 경우도 "한 번 찾아보고 없으면 포기"가 아니라, 짧은 간격으로 몇 번 더 찾아보는 재시도가 필요한 대표적인 상황입니다.

🔍 예시
카카오 프록시를 호출하는 background.js에 재시도와 지수 백오프를 더하면 대략 이런 모습이 됩니다.

  async function fetchWithRetry(url, maxRetries = 3) {
    for (let attempt = 0; attempt < maxRetries; attempt++) {
      try {
        const res = await fetch(url);
        if (!res.ok) throw new Error(`상태 코드 ${res.status}`);
        return await res.json();
      } catch (err) {
        if (attempt === maxRetries - 1) {
          console.error("카카오 프록시 호출 최종 실패:", err);
          throw err;
        }
        const waitMs = 1000 * Math.pow(2, attempt);
        await new Promise((resolve) => setTimeout(resolve, waitMs));
      }
    }
  }

세 번까지는 1초, 2초, 4초씩 간격을 늘려가며 다시 걸어보고, 그래도 안 되면 콘솔에 실패 기록을 남긴 뒤 포기합니다. 이 콘솔 기록이 바로 내일 배울 로깅의 가장 작은 첫걸음입니다.

📝 오늘의 한 줄 정리
자동화는 실패가 일어나지 않으리라 가정하고 짜는 것이 아니라, 실패를 미리 예상하고 언제까지 다시 시도하고 언제 포기해서 그 사실을 알릴지를 함께 설계하는 것입니다.

🙋 초보자가 자주 헷갈리는 점
재시도를 많이 걸수록 무조건 안전하다고 생각하기 쉽지만, 실제로는 그렇지 않은 경우가 있습니다. 예를 들어 결제나 신청서 제출처럼 "성공했는지 확실치 않은 요청"을 결과 확인 없이 그대로 재시도하면, 이미 한 번 성공한 요청이 중복으로 한 번 더 처리되어 여비가 두 번 신청되는 것 같은 사고가 날 수 있습니다. 그래서 실무에서는 재시도해도 안전한 요청(예: 단순 조회)과 재시도 전에 반드시 결과를 먼저 확인해야 하는 요청(예: 신청·결제)을 구분해서 다룹니다.

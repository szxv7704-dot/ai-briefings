📚 오늘의 학습 주제 : 심화 22일차 · 브라우저 확장(Chrome Extension) 자동화 실전, manifest.json 권한과 background.js를 실제 배포 엔드포인트에 연결하기 (2026-09-13)

📌 어제 배운 내용과의 연결
어제는 카카오 프록시 코드를 push하면 워크플로우 파일이 테스트를 통과했을 때만 Vercel 프로덕션 주소로 자동 배포해준다는 것을 배웠는데, 오늘은 바로 그렇게 배포되어 실제로 살아 움직이는 그 주소를 크롬 확장의 개인 비서가 정확히 어떤 권한 서류를 들고 있어야 전화를 걸 수 있는지를 봅니다.

🎯 오늘 배울 개념
매니페스트 V3(Manifest V3, 크롬 확장이 지켜야 하는 최신 보안 규격) 체제에서는 코드 안에 fetch로 어떤 주소를 부르겠다고 적는 것만으로는 부족하고, manifest.json의 host_permissions(호스트 권한, 배경 스크립트가 실제로 네트워크 요청을 걸어도 되는 도메인 목록을 브라우저에 미리 신고해두는 항목)에 그 주소를 정확히 등록해야만 전화가 실제로 연결된다는 구조, 그리고 콘텐츠 스크립트와 백그라운드 스크립트와 배포된 서버리스 함수와 재시도 로직 네 가지가 메시지 전달로 한 줄에 엮이는 전체 흐름

━━━━━━━━━━━━━━━━━━━━

19일차와 22일차에서 크롬 확장을 각 직원 책상 옆에 붙은 개인 비서에 비유했습니다. 이 비서는 회사 정문 경비실(브라우저)의 승인을 받아야 출입증을 발급받는데, 그 출입증에는 두 가지 서로 다른 도장이 찍혀 있습니다. 하나는 "이 문서(웹페이지)에는 들어가도 된다"는 도장이고, 다른 하나는 "이 전화번호(외부 서버 주소)로는 걸어도 된다"는 도장입니다. 매니페스트 V3 이전에는 이 두 도장을 한데 뭉쳐서 찍었지만, 지금은 보안이 강화되면서 반드시 따로따로 찍어야 합니다. 그래서 비서의 코드 안에 아무리 "카카오 프록시 서버에 전화를 걸어라"라고 적어놓아도, 출입증의 host_permissions 칸에 그 서버 주소가 정확히 도장 찍혀 있지 않으면 경비실이 그 전화 자체를 끊어버립니다. 더 까다로운 점은, 어제 CI/CD로 배포된 카카오 프록시 주소가 만약 새 프로젝트로 다시 만들어지거나 커스텀 도메인으로 바뀌면, 출입증에 적힌 옛 주소로는 더 이상 전화가 연결되지 않는다는 것입니다. 즉 서버 쪽 주소가 바뀌는 순간, 코드뿐 아니라 출입증(manifest.json)도 함께 갱신해줘야 비서가 계속 일할 수 있습니다.

🛠 실전 연결
여러분의 여비 계산기 확장을 실제로 완성하려면 도구 네 개가 한 줄로 이어져야 합니다. 첫째, 사내 출장신청 페이지가 열리면 content.js가 여비 입력란을 찾아 채웁니다. 둘째, 로그인이 끝나면 content.js는 직접 카카오 프록시에 전화를 걸지 않고, chrome.runtime.sendMessage로 뒤편 대기실의 background.js에 "로그인 끝났어요"라고만 전달합니다. 셋째, background.js가 어제 CI/CD로 배포된 실제 주소(https://kakao-proxy.vercel.app)에 전화를 걸되, 23일차에 배운 지수 백오프 재시도를 그대로 재사용해서 한 번에 안 되면 몇 번 더 시도합니다. 넷째, manifest.json의 host_permissions에 그 배포 주소가 정확히 등록되어 있어야 셋째 단계의 전화 자체가 끊기지 않습니다. 콘텐츠 스크립트가 직접 fetch하지 않고 굳이 백그라운드에 메시지로 넘기는 이유도 분명합니다. 콘텐츠 스크립트는 사내 인트라넷 페이지 안에서 실행되는데, 그 페이지의 보안 정책이 외부 카카오 주소로의 요청을 막아버릴 수 있어서, 그런 제약이 없는 대기실 쪽(백그라운드)에 전화를 대신 걸게 하는 것입니다.

🔍 예시
manifest.json에서는 permissions와 host_permissions를 이렇게 나눠 적습니다.

  {
    "manifest_version": 3,
    "name": "여비 계산기 자동입력",
    "permissions": ["storage"],
    "host_permissions": ["https://kakao-proxy.vercel.app/*"],
    "content_scripts": [
      { "matches": ["https://intranet.jbe.go.kr/travel/*"], "js": ["content.js"] }
    ],
    "background": { "service_worker": "background.js" }
  }

content.js는 이제 전화를 직접 걸지 않고 메시지만 보냅니다.

  document.querySelector("#kakao-login-btn").addEventListener("click", () => {
    chrome.runtime.sendMessage({ type: "KAKAO_LOGIN_DONE" });
  });

background.js는 메시지를 받으면, 23일차에 만든 fetchWithRetry를 그대로 불러와 실제 배포 주소로 전화를 걸고, 성공하면 결과를 저장해서 content.js가 나중에 꺼내 쓸 수 있게 합니다.

  chrome.runtime.onMessage.addListener((message) => {
    if (message.type === "KAKAO_LOGIN_DONE") {
      fetchWithRetry("https://kakao-proxy.vercel.app/api/token")
        .then((data) => chrome.storage.local.set({ accessToken: data.access_token }))
        .catch((err) => console.error("카카오 토큰 요청 최종 실패:", err));
    }
  });

만약 host_permissions 줄을 빼먹으면, fetchWithRetry 안의 fetch 자체가 네트워크 단계에서 막혀서 세 번 재시도해도 전부 실패하는데, 코드만 봐서는 이유를 알기 어렵고 크롬 개발자 도구의 콘솔에 찍히는 차단 메시지를 봐야 원인을 찾을 수 있습니다.

📝 오늘의 한 줄 정리
매니페스트 V3 체제에서 백그라운드 스크립트가 외부 서버에 전화를 걸려면 코드뿐 아니라 manifest.json의 host_permissions에도 그 주소를 정확히 등록해야 하며, 콘텐츠·백그라운드·배포된 서버·재시도 로직이 메시지 전달로 한 줄에 이어질 때 비로소 확장이 완성됩니다.

🙋 초보자가 자주 헷갈리는 점
permissions는 storage나 tabs처럼 브라우저 자체 기능을 쓸 권한이고, host_permissions는 특정 인터넷 주소로 네트워크 요청을 걸 권한이라서 서로 다른 종류인데, 옛날 매니페스트 V2 자료를 보고 이 둘을 한 줄에 합쳐 적다가 배포된 서버 요청만 계속 막히는 경우가 흔합니다. 또한 host_permissions에 주소를 등록해도 실제 배포 주소와 철자 하나, 슬래시 하나만 달라도 전화가 연결되지 않으므로, 어제 CI/CD로 배포가 끝난 뒤에는 반드시 Vercel 대시보드에 뜬 실제 주소를 그대로 복사해와야 합니다.

💬 내일 예고
내일은 심화 23일차로, 5부의 시작이자 오늘 만든 fetchWithRetry를 한 단계 더 다듬어서, 같은 요청을 무한정 반복하지 않도록 막는 회로 차단기(Circuit Breaker) 개념과, 신청·결제처럼 중복 실행되면 위험한 작업을 안전하게 재시도하는 멱등성(Idempotency) 처리까지 더 깊이 들어갑니다.

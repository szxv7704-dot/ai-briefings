📌 어제 배운 내용과의 연결
어제는 조립라인(노코드)이 대부분을 처리하다가 애매한 상자만 옆문으로 빼서 MCP로 연결된 에이전트에게 넘긴다는 파이프라인을 봤는데, 오늘은 그 옆문을 열고 들어가 에이전트의 판단 코드가 실제로 어떤 서버 위에서, 어떤 시간 제한을 안고 돌아가는지를 뜯어봅니다.

🎯 오늘 배울 개념
서버리스 함수(Serverless Function)가 요청이 없을 때 정말로 완전히 잠들어 있다가 처음 깨어날 때 생기는 지연인 콜드 스타트(Cold Start, 오랫동안 쉬던 함수가 첫 요청을 받고 실행 준비를 마치기까지 걸리는 시간)와, 한 번 깨어난 함수라도 무한정 계속 돌 수는 없게 정해둔 실행 시간 제한(Timeout, 함수 하나가 한 번 실행될 때 허용되는 최대 시간)이, 어제 본 "에이전트 판단 구간"을 서버리스 함수 위에 올릴 때 왜 반드시 고려해야 하는 조건이 되는지

━━━━━━━━━━━━━━━━━━━━

19일차에 서버리스 함수를 "회의가 잡힐 때만 잠깐 문이 열리는 공유 회의실"에 비유했습니다. 오늘은 그 회의실 문이 정말로 오랫동안 아예 열린 적이 없을 때 어떤 일이 벌어지는지를 봅니다. 회의실을 오래 안 쓰면 건물 관리소는 그 층의 냉난방과 조명 시스템을 아예 꺼버립니다. 그러다 갑자기 손님이 초인종을 누르면, 관리소는 먼저 꺼져 있던 시스템을 다시 켜고 방 온도를 맞춘 뒤에야 손님을 들여보낼 수 있습니다. 이 "다시 켜고 맞추는" 짧은 지연이 콜드 스타트입니다. 반대로 바로 직전에 다른 손님이 다녀가서 방이 아직 따뜻하면, 관리소는 시스템을 다시 켤 필요 없이 곧장 문을 열어줍니다. 이걸 웜 스타트(Warm Start, 이미 켜져 있던 함수가 지연 없이 바로 응답하는 상태)라 부릅니다. 그리고 회의실 예약 자체에도 규칙이 있습니다. 아무리 급한 회의라도 한 번 예약하면 최대 10분, 길어도 몇십 분 안에는 반드시 방을 비워줘야 합니다. 이게 실행 시간 제한이며, 이 시간을 넘기면 관리소가 강제로 불을 끄고 손님을 내보냅니다. 어제 본 에이전트 판단 구간, 즉 영수증을 읽고 과거 기록과 대조해서 판단을 내리는 그 작업도 결국 이 회의실 안에서 벌어집니다. 그런데 에이전트의 판단은 조건문 한 줄을 확인하는 것과 달리 모델이 문장을 읽고 생각하는 시간이 걸리고, 그 판단 중간에 MCP로 다른 서비스에 자료를 더 물어보러 나갔다 오기까지 하니, 이 짧은 회의실 예약 시간 안에 다 끝낼 수 있느냐가 실제로 신경 써야 할 문제가 됩니다.

🛠 실전 연결
어제 예시의 2단계, "애매한 영수증 항목 판단"을 맡은 Agent() 호출을 실제로 Vercel 서버리스 함수 위에 올린다고 생각해봅시다. 이 함수는 평소에는 완전히 잠들어 있다가, Zapier의 조립라인이 "이 상자는 옆문으로"라고 판단해 웹훅으로 호출하는 그 순간에만 깨어납니다. 오래간만에 호출되는 함수라면 콜드 스타트가 걸려 응답까지 1~2초가 더 걸릴 수 있고, 에이전트가 판단 과정에서 Google Sheets MCP 도구를 불러 과거 기록을 조회하고, 다시 그 결과를 보고 최종 판단까지 내리는 전체 과정이 기본 실행 시간 제한 안에 끝나야 합니다. 만약 이 시간을 넘기면 관리소가 강제로 불을 끄듯 함수가 중간에 강제 종료되어, 에이전트가 판단을 다 못 내린 채로 Sheets 행이 반쯤만 채워지는 사고가 날 수 있습니다. 그래서 실제 배포에서는 이 함수의 실행 시간 제한을 기본값보다 넉넉하게 늘려 설정해두는 경우가 많습니다. Kakao 프록시처럼 카카오 서버에 토큰 하나만 물어보고 바로 답하는 단순한 함수는 기본 제한으로도 충분하지만, 에이전트가 여러 단계를 생각하고 도구를 여러 번 오가며 판단하는 함수는 애초에 설계할 때부터 이 시간 제한을 염두에 둬야 한다는 점이 오늘의 실전 연결입니다.

🔍 예시
Vercel에 어제 본 판단 에이전트 함수를 올린다면, 함수 코드 옆에 이런 설정 파일이 함께 배포됩니다.

  vercel.json
  {
    "functions": {
      "api/judge-receipt.js": {
        "maxDuration": 60
      }
    }
  }

  api/judge-receipt.js
  export default async function handler(req, res) {
    const { merchant, amount, timestamp } = req.body;

    const result = await client.messages.create({
      model: "claude-sonnet-5",
      system: "영수증과 최근 30일 출장 일정을 대조해
               출장 지출인지 판단하고, category 필드를
               채워 Sheets 행을 업데이트하라",
      tools: [sheetsReadTool, sheetsWriteTool],
      messages: [{ role: "user", content:
        `${merchant} / ${amount}원 / ${timestamp}` }]
    });

    res.status(200).json({ done: true });
  }

여기서 maxDuration: 60은 이 함수가 최대 60초까지 실행을 허용받는다는 뜻이며, 기본값(보통 10초 안팎)만으로는 에이전트가 도구를 오가며 판단하기에 빠듯하기 때문에 일부러 늘려둔 것입니다. 반대로 콜드 스타트 자체를 줄이고 싶다면, 이 함수를 완전히 재우는 대신 일정 시간 간격으로 살짝 깨워두는 예약(6일차에 배운 스케줄링)을 따로 걸어두는 방법도 실전에서 자주 씁니다.

📝 오늘의 한 줄 정리
서버리스 함수는 평소엔 완전히 잠들어 있다가 깨어날 때 콜드 스타트라는 지연을 치르고, 한 번 깨어나도 정해진 실행 시간 제한 안에 일을 끝내야 하므로, 조건문 한 줄이 아니라 여러 단계를 생각하고 도구를 오가는 에이전트 판단 구간을 올릴 때는 이 두 가지를 미리 설계에 반영해야 합니다.

🙋 초보자가 자주 헷갈리는 점
서버리스라서 "항상 빠르게 즉시 응답한다"고 오해하기 쉬운데, 실제로는 오래 쉬었던 함수일수록 콜드 스타트 때문에 첫 응답이 오히려 평소보다 느려질 수 있습니다. 또 하나 흔한 착각은 실행 시간 제한을 "느린 코드를 걸러내는 에러 방지 장치" 정도로만 생각하는 것인데, 사실은 회의실을 한 손님이 너무 오래 붙잡고 있으면 다음 손님이 못 들어오는 것을 막기 위한 자원 배분 규칙에 가깝습니다. 그래서 시간 제한에 자주 걸린다면 그 시간을 무작정 늘리기보다, 애초에 한 함수가 너무 많은 판단을 한 번에 떠맡고 있지는 않은지부터 점검하는 것이 먼저입니다.

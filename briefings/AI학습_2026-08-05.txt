📚 오늘의 학습 주제 : 8일차 · [1부 총정리] 지금까지 배운 개념을 하나의 예시 자동화 시나리오로 엮어서 복습 (2026-08-05)

📌 어제 배운 내용과의 연결
어제는 자동화가 외부 저장소에 기록을 남겨두면 마치 기억하는 것처럼 동작한다는 상태(state) 저장을 배웠으니, 오늘은 그것을 포함해 1부에서 배운 일곱 개의 개념을 하나로 모아 처음부터 끝까지 이어지는 완결된 자동화 시나리오로 복습합니다.

🎯 오늘 배울 개념
자동화·트리거·액션·워크플로우·API·웹훅·스케줄링·상태 저장, 이 일곱 개념이 실제로는 서로 남남이 아니라 하나의 자동화 안에서 동시에 맞물려 돌아가는 여러 층(layer)이라는 것

━━━━━━━━━━

지난 7일 동안 배운 공장 조립라인을 하루치 전체 흐름으로 이어서 한 번에 재생해 보겠습니다. 새벽 6시, 아무도 출근하지 않은 공장에서 벽시계가 6시를 가리키는 순간(스케줄링·cron) 컨베이어 벨트 전원이 저절로 켜집니다. 전원이 켜지기 전, 라인 제어 시스템은 먼저 야간 근무일지(외부 저장소)를 펼쳐 "어제 6번째 부품까지 조립했다"는 기록을 읽어옵니다(상태 저장). 그래야 오늘 7번째 부품부터 이어서 조립할 수 있기 때문입니다. 근무일지를 확인한 시스템은 이제 벨트를 실제로 돌리기 시작합니다. 부품이 벨트 위에 놓이는 순간(트리거)을 센서가 감지하면 로봇 팔이 용접을 시작합니다(액션). 용접이 끝난 차체는 다음 공정인 도색으로 넘어가고, 그곳에서 다시 "차체 도착"이 트리거가 되어 "도색"이라는 액션이 실행되며, 이런 트리거-액션 쌍이 조립·검사까지 사슬처럼 이어져 하나의 완결된 워크플로우를 이룹니다. 이 워크플로우 안에서 용접 로봇과 도색 로봇이 차체 정보를 주고받을 때는 반드시 정해진 규격(API)을 따르고, 마지막 검사 공정에서 불량품이 발견되면 관리자가 계속 지켜보지 않아도 검사 센서가 즉시 관리자의 휴대폰으로 알림을 쏘아 보냅니다(웹훅). 즉 오늘 하루 라인이 돌아가기까지 스케줄링이 문을 열고, 상태 저장이 어제와 오늘을 이어주고, 트리거와 액션이 짝을 이루어 움직이고, 그 짝들이 워크플로우로 엮이고, 그 안에서 API가 규격을 지키며 대화하고, 웹훅이 예외 상황을 즉시 알려준 것입니다. 일곱 개념은 순서대로 배운 별개의 기술이 아니라, 자동화라는 하나의 건물을 이루는 서로 다른 층이었던 셈입니다.

🛠 실전 연결
이 일곱 개념을 여러분이 이미 살펴본 네 가지 실제 사례에 겹쳐 보면 각 사례가 이 층들 중 어디를 쓰고 어디를 안 쓰는지가 뚜렷해집니다.
• Claude Routines 학습 브리핑 파이프라인 — 스케줄링(cron)으로 매일 시작하고, 상태 저장(저장소의 어제 파일)으로 일차를 이어가며, "저장소 조회→일차 추출→글 작성→커밋"이라는 워크플로우 전체가 GitHub API 호출로 이루어집니다. 다만 이 파이프라인 자체는 웹훅을 쓰지 않고 정해진 시각에만 움직입니다.
• 여비 계산기 — 사용자가 영수증을 업로드하는 트리거와 금액을 계산해 보여주는 액션만 있는, 상태 저장도 스케줄링도 없는 가장 단순한 형태에 가깝습니다.
• 크롬 확장 — 사용자가 특정 페이지를 여는 것이 트리거, 스크립트 실행이 액션이며, 필요한 데이터를 가져올 때 API를 호출합니다.
• Kakao 프록시 — 사용자가 로그인 버튼을 누르면(트리거) 카카오 서버로 요청을 보내고(API), 로그인이 완료되는 순간 카카오가 먼저 콜백 주소로 결과를 알려주는 웹훅 방식으로 응답을 받습니다.
이처럼 모든 자동화가 일곱 층을 다 쌓을 필요는 없고, 목적에 맞는 층만 골라 쌓으면 됩니다.

🔍 예시
학습 브리핑 파이프라인 하나에 일곱 개념이 어떻게 겹쳐 있는지 순서대로 표시하면 다음과 같습니다.

  0. [자동화] 사람 개입 없이 아래 전체가 자동으로 실행됨
  1. [스케줄링] cron_expression: "0 9 * * *" → 매일 오전 9시 시작
  2. [상태 저장] GitHub API로 learning-log 브랜치의 최신 파일 조회
  3. [트리거→액션] "최신 파일을 찾았다"가 트리거, "일차 번호를 읽어 +1 한다"가 액션
  4. [워크플로우] 조회 → 일차 추출 → 글 작성 → 파일 커밋, 4단계가 순서대로 연결
  5. [API] create_or_update_file API 호출로 저장소에 실제 파일 기록
  6. [웹훅 미사용] 이 파이프라인은 이벤트 알림 대신 시간 예약만으로 충분해 웹훅은 쓰지 않음

이렇게 표를 그려보면 "이 자동화에는 어떤 층이 있고 어떤 층이 빠져 있는가"를 스스로 점검할 수 있습니다.

📝 오늘의 한 줄 정리
자동화·트리거·액션·워크플로우·API·웹훅·스케줄링·상태 저장은 따로 배운 여덟 단어가 아니라, 하나의 자동화가 실제로 돌아가기 위해 필요에 따라 골라 쌓는 서로 다른 층입니다.

🙋 초보자가 자주 헷갈리는 점
1부를 순서대로 배우다 보면 이 여덟 개념이 항상 정해진 순서(자동화→트리거→...→상태)로 함께 등장해야 한다고 오해하기 쉽지만, 실제 자동화는 이 중 필요한 몇 개만 골라 씁니다. 여비 계산기처럼 트리거와 액션만으로도 충분히 쓸모 있는 자동화가 완성되며, 모든 층을 다 쌓아야 "진짜" 자동화인 것은 아닙니다. 또한 오늘 정리한 순서는 개념을 이해하기 위한 배치일 뿐, 실제 설계할 때는 목적(무엇을 자동화할 것인가)을 먼저 정한 뒤 필요한 층을 거꾸로 골라 쌓는 것이 자연스러운 순서입니다.

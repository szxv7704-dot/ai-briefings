📚 오늘의 학습 주제 : 심화 20일차 · 환경변수(Environment Variable)와 보안, 로컬 .env부터 Vercel·GitHub Secrets까지 세 곳 비교 (2026-09-11)

📌 어제 배운 내용과의 연결
어제 본 judge-receipt.js 코드에는 client.messages.create()를 호출하는 부분이 있었는데, 이 호출이 실제로 동작하려면 API 키가 필요하며, 오늘은 그 키를 코드 안에 직접 적지 않고 어디에 숨겨서 관리하는지를 봅니다.

🎯 오늘 배울 개념
환경변수(Environment Variable, 코드 파일 안이 아니라 실행 환경이 코드에게 별도로 건네주는 설정값)를 써서 API 키 같은 비밀정보(시크릿, Secret)를 코드에서 분리해야 하는 이유와, 그 값이 로컬 개발 환경의 .env 파일, 배포 서버(Vercel)의 환경변수 설정 화면, 그리고 GitHub Secrets 이 세 곳에서 각각 다른 방식으로 저장되고 전달되는 구조

━━━━━━━━━━━━━━━━━━━━

어제 서버리스 함수를 "회의가 잡힐 때만 문이 열리는 공유 회의실"에 비유했습니다. 그 회의실에 들어가려면 출입 비밀번호가 필요한데, 초보자가 흔히 저지르는 실수는 이 비밀번호를 아예 문 앞에 포스트잇으로 붙여두는 것입니다. 즉 코드 파일 맨 위에 apiKey = "sk-abc123..." 처럼 실제 키 값을 그대로 적어버리는 것입니다. 이렇게 하면 그 코드를 열어보는 누구나, 심지어 GitHub에 공개로 올려버리면 전 세계 누구나 그 비밀번호로 회의실 문을 열 수 있게 됩니다. 환경변수는 이 문제를 건물 관리소 시스템으로 해결합니다. 비밀번호를 문에 붙여두지 않고, 관리소(실행 환경)가 별도의 금고에 보관해두었다가, 회의실 문이 열릴 때마다 "이번엔 이 손님이니 이 비밀번호를 알려줄게" 하고 그 순간에만 코드에게 값을 건네주는 방식입니다. 코드 자체에는 "이 값은 나중에 관리소가 알려줄 것"이라는 자리표시자만 남아 있을 뿐, 실제 값은 코드 파일 어디에도 적혀 있지 않습니다. 그런데 이 관리소가 한 곳만 있는 게 아니라는 점이 오늘의 핵심입니다. 내가 노트북에서 코드를 짜며 테스트할 때 쓰는 동네 관리소(로컬 .env 파일), 실제로 배포된 회의실 건물을 관리하는 본사 관리소(Vercel 환경변수 설정), 그리고 코드를 새로 배포할 때마다 자동으로 작업하는 공사 인력에게만 잠깐 건네주는 현장 관리소(GitHub Secrets)가 각각 따로 존재하며, 같은 이름의 비밀번호라도 세 곳에 따로따로 등록해둬야 합니다.

🛠 실전 연결
Kakao 프록시 사례를 떠올려보면, 이 프록시 함수는 카카오 서버에 토큰을 요청할 때 KAKAO_CLIENT_SECRET 값이 필요합니다. 개발 단계에서는 이 값을 로컬 컴퓨터의 .env 파일에 적어두고 테스트하고, 실제 배포판에서는 같은 값을 Vercel 대시보드의 환경변수 설정 화면에 등록해서 서버가 실행될 때 읽어가게 합니다. 그리고 만약 이 프록시 코드를 GitHub Actions로 자동 배포하는 CI/CD 파이프라인(21일차에 다룰 내용)을 쓴다면, 배포 과정 중에 테스트를 돌리기 위해 같은 비밀값을 GitHub Secrets에도 한 번 더 등록해야 합니다. 즉 하나의 자동화(Kakao 프록시)를 완성하려면 같은 비밀번호를 로컬, 배포 서버, 배포 파이프라인 이렇게 세 금고에 각각 넣어둬야 하고, 어느 한 곳이라도 빠지면 그 단계에서 "키를 찾을 수 없다"는 에러가 나게 됩니다.

🔍 예시
로컬 개발 환경에서는 프로젝트 폴더에 .env 파일을 만들어 이렇게 적어둡니다. 이 파일은 반드시 .gitignore에 등록해서 GitHub에 절대 올라가지 않게 해야 합니다.

  .env
  ANTHROPIC_API_KEY=sk-ant-실제값
  KAKAO_CLIENT_SECRET=카카오시크릿값

  judge-receipt.js (수정판)
  const client = new Anthropic({
    apiKey: process.env.ANTHROPIC_API_KEY
  });

  kakao-proxy.js
  const kakaoToken = await fetch("https://kauth.kakao.com/oauth/token", {
    method: "POST",
    body: new URLSearchParams({
      client_secret: process.env.KAKAO_CLIENT_SECRET,
      grant_type: "authorization_code"
    })
  });

여기서 코드에는 실제 값이 아니라 process.env.ANTHROPIC_API_KEY라는 자리표시자만 있습니다. 배포 서버인 Vercel에서는 프로젝트 대시보드의 Settings → Environment Variables 화면에서 이름(ANTHROPIC_API_KEY)과 값을 각각 입력창에 채워 등록하며, Production과 Preview 환경을 따로 나눠 등록할 수 있습니다. GitHub Actions로 CI/CD를 구성했다면, 저장소의 Settings → Secrets and variables → Actions 화면에서 같은 이름으로 값을 등록해두고, 워크플로우 파일에서는 이렇게 불러옵니다.

  .github/workflows/deploy.yml
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}

세 곳 모두 코드 파일 안에는 값이 전혀 노출되지 않는다는 공통점이 있지만, 등록하는 화면과 그 값을 읽어갈 수 있는 대상(로컬 실행, 배포된 서버, 배포 작업 그 자체)이 서로 다르다는 점이 오늘 비교의 핵심입니다.

📝 오늘의 한 줄 정리
비밀정보는 코드 파일에 직접 적지 않고 환경변수로 분리해야 하며, 같은 값이라도 로컬 .env, Vercel 환경변수 설정, GitHub Secrets라는 서로 다른 세 금고에 각각 등록해야 각 실행 환경에서 정상적으로 읽어갈 수 있습니다.

🙋 초보자가 자주 헷갈리는 점
.env 파일에 값을 한 번 적어두면 배포 서버에도 자동으로 전달된다고 착각하기 쉬운데, .env 파일은 보통 .gitignore에 의해 GitHub에 아예 올라가지 않으므로 Vercel이나 GitHub Actions는 그 파일의 존재 자체를 알지 못합니다. 그래서 로컬에서만 테스트가 잘 되다가 실제 배포 후 "환경변수를 찾을 수 없다"는 에러가 나는 경우가 아주 흔하며, 이럴 때는 코드를 의심하기 전에 배포 서버 쪽 설정 화면에 그 값을 따로 등록했는지부터 확인해야 합니다.

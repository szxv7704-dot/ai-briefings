📚 오늘의 학습 주제 : 심화 2일차 · 트리거(Trigger)와 액션(Action) — 하나의 신호가 여러 곳으로 동시에 퍼질 때 (2026-08-24)

📌 어제 배운 내용과의 연결
어제는 자동화의 본질이 "조건문 하나 + 실행문 하나"라는 것을 실제 코드로 확인했고, 오늘은 그 실행문이 하나가 아니라 여러 개일 때, 즉 트리거 하나에 액션 여러 개가 동시에 연결된 경우를 실제 코드로 확인합니다.

🎯 오늘 배울 개념
트리거(Trigger, 자동화를 시작시키는 신호) 하나가 액션(Action, 트리거에 반응해 실제로 실행되는 작업) 여러 개를 동시에 실행시키는 구조, 그리고 그중 하나가 실패했을 때 나머지 액션들의 운명이 서로 어떻게 달라지는지를 깊이 파고들기

━━━━━━━━━━━━━━━━

2일차에 배웠던 안내 데스크 센서 비유를 다시 꺼내 보겠습니다. 그때는 손님이 들어오면(트리거) 직원 한 명을 호출한다(액션)는 단순한 구조로 설명했습니다. 그런데 실제 회사라면 손님 한 명이 들어왔을 때 벌어지는 일이 그렇게 단순하지 않습니다. 안내 직원 호출, 보안팀에 출입 기록 통보, 방문 일지 자동 기록. 이 세 가지가 전부 같은 순간, 같은 트리거에서 동시에 뻗어나갑니다. 이렇게 신호 하나가 여러 갈래로 동시에 퍼져나가는 구조를 팬아웃(Fan-out, 트리거 하나가 여러 액션으로 동시에 갈라지는 것)이라고 부릅니다. 여기서 중요한 질문이 하나 생깁니다. 만약 방문 일지 기록 시스템이 그날따라 고장 나 있다면 어떻게 될까요. 안내 직원 호출과 보안팀 통보까지 같이 멈춰버려야 할까요, 아니면 그 두 가지는 정상적으로 진행되어야 할까요. 정답은 후자입니다. 액션들은 서로 독립적으로 실행되어야지, 하나가 넘어졌다고 나머지 전부가 같이 넘어져서는 안 됩니다. 프로그래밍에서는 이렇게 여러 작업을 동시에 실행하는 것을 병렬 실행(Parallel Execution, 여러 작업을 순서대로가 아니라 동시에 처리하는 방식)이라고 부르고, 각 작업의 성공과 실패를 서로 분리해서 처리하도록 짜는 것이 핵심 설계 원칙입니다.

🛠 실전 연결
크롬 확장의 background.js를 다시 떠올려 보면, 카카오 로그인이 성공하는 순간(트리거) 실제로는 한 가지 일만 일어나지 않습니다. 첫째, chrome.storage에 토큰을 저장합니다. 둘째, content.js에 메시지를 보내 화면의 로그인 버튼을 갱신합니다. 셋째, 있다면 로그인 로그를 서버로 전송합니다. 이 세 가지 중에서 토큰 저장은 실패하면 로그인 자체가 무의미해지는 핵심 액션이지만, 로그인 로그 전송은 실패해도 사용자 입장에서는 아무 문제 없이 계속 여비 계산기를 쓸 수 있어야 합니다. 즉 액션마다 실패했을 때의 무게가 다르다는 것을 설계 단계에서 미리 구분해 둬야 합니다. Claude Routines 쪽도 마찬가지입니다. 오늘 이 브리핑이 만들어지는 과정에서도 스케줄이라는 트리거 하나가 최소 두 갈래의 액션으로 갈라질 수 있습니다. GitHub 저장소에 파일을 커밋하는 것과, 필요하다면 사용자에게 완료를 알리는 것입니다. 이 둘은 서로 다른 시스템이므로, 커밋이 늦어진다고 알림 시스템까지 덩달아 멈춰서는 안 됩니다.

🔍 예시
크롬 확장 background.js에서 카카오 로그인 성공 트리거가 세 개의 액션으로 갈라지는 상황을 코드로 옮기면 다음과 같습니다.

  chrome.runtime.onMessage.addListener((message) => {
    if (message.type !== 'KAKAO_LOGIN_SUCCESS') return

    Promise.allSettled([
      saveTokenToStorage(message.token),
      notifyContentScript(message.token),
      sendLoginLog(message.token)
    ]).then((results) => {
      results.forEach((result, i) => {
        if (result.status === 'rejected') {
          console.warn(`액션 ${i}번 실패:`, result.reason)
        }
      })
    })
  })

여기서 핵심은 Promise.allSettled입니다. 이 함수는 배열 안의 여러 액션을 동시에 실행하되, 하나가 실패하더라도 나머지 액션들의 결과를 끝까지 기다렸다가 각각의 성공과 실패를 따로따로 알려줍니다. 만약 이 자리에 Promise.all을 썼다면 이야기가 달라집니다. Promise.all은 액션 중 단 하나만 실패해도 전체를 실패로 처리해버려서, saveTokenToStorage가 성공했는데도 그 결과까지 함께 묻혀버릴 수 있습니다. 로그인의 핵심인 토큰 저장과, 있으면 좋고 없어도 그만인 로그 전송을 같은 무게로 묶어버리는 실수인 셈입니다.

📝 오늘의 한 줄 정리
트리거 하나에 액션이 여러 개 연결될 때는 액션들을 서로 독립적으로 설계해서, 하나의 실패가 나머지 전체를 무너뜨리지 않도록 하는 것이 핵심이다.

🙋 초보자가 자주 헷갈리는 점
액션이 여러 개면 당연히 위에서부터 순서대로 하나씩 실행된다고 생각하기 쉽습니다. 하지만 실제로는 동시에, 즉 병렬로 실행되는 경우가 많아서 어떤 액션이 먼저 끝날지 코드만 봐서는 보장할 수 없습니다. 순서가 반드시 중요한 작업, 예를 들어 토큰을 저장한 다음에야 화면을 갱신해야 하는 경우라면 일부러 순서를 강제하는 코드를 따로 짜야 하며, 그냥 나열만 해두면 예상과 다른 순서로 실행되어 원인을 찾기 어려운 오류로 이어질 수 있습니다.

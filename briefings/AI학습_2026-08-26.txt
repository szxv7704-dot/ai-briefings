📌 어제 배운 내용과의 연결
어제는 워크플로우 안에서 getLatestFileFromGithub 같은 함수 호출이 반드시 다른 액션보다 먼저 끝나야 한다는 의존성을 코드로 확인했으니, 오늘은 그 함수 호출 한 줄 한 줄이 실제로는 어떤 요청과 응답 형식을 주고받는지 구체적으로 파고듭니다.

🎯 오늘 배울 개념

4일차에 레스토랑 비유로 API를 "메뉴판을 보고 주문하는 것"이라고 배웠습니다. 오늘은 그 메뉴판을 실제 주문서 한 장으로 펼쳐보겠습니다. 손님이 종업원에게 그냥 "김치찌개 주세요"라고 말만 하는 게 아니라, 실제로는 주문서에 몇 가지 항목을 정확히 채워 넣습니다. 주문 종류(포장인지 매장인지, 이것이 메서드입니다), 테이블 번호(요청이 향할 정확한 주소), 손님의 회원 카드 제시(신원을 증명하는 헤더), 그리고 "맵기 조절 : 보통, 수량 : 1인분"처럼 세부 내용을 적은 메모(바디)입니다. 주방은 이 주문서를 받고 나서 반드시 접수증을 돌려줍니다. 접수증 맨 위에는 "정상 접수"인지 "품절"인지 "회원 카드 확인 불가"인지를 나타내는 도장(상태 코드)이 찍혀 있고, 그 아래에는 실제 준비된 음식 내용이나 오류 사유(바디)가 적혀 있습니다. 어제 코드에 등장했던 getLatestFileFromGithub라는 이름도 사실 이 주문서 한 장을 자동으로 채워서 GitHub라는 주방에 보내고, 접수증을 받아서 해석하는 함수일 뿐입니다. 이름은 근사해 보여도 뜯어보면 정해진 형식의 종이 한 장을 주고받는 것이 전부입니다.

🛠 실전 연결
어제 워크플로우 코드에서 한 줄로 뭉뚱그려 있던 getLatestFileFromGithub(learning-log, briefings)는, 실제로는 GitHub 저장소 API 주소로 GET 요청 하나를 보내는 일입니다. 이 요청서에는 어떤 저장소, 어떤 브랜치, 어떤 폴더인지가 주소와 바디에 나뉘어 담기고, 헤더에는 이 요청을 보낼 자격이 있다는 것을 증명하는 인증 토큰이 회원 카드처럼 실려 갑니다. 여비 계산기 쪽도 똑같습니다. 크롬 확장이 카카오 로그인 코드를 받은 뒤, Kakao 프록시 서버리스 함수는 카카오 인증 서버에 "이 코드를 access_token으로 바꿔줘"라는 주문서(POST 요청)를 보내고, 카카오 서버는 접수증(응답)에 성공 도장과 함께 실제 토큰 값을 담아 돌려줍니다. 겉으로는 서로 완전히 다른 서비스(GitHub, 카카오)처럼 보여도, 주고받는 종이의 형식(요청과 응답)은 똑같은 틀을 따르고 있습니다.

🔍 예시
어제 한 줄이었던 getLatestFileFromGithub의 실제 내부를 요청과 응답 형식까지 펼쳐보면 다음과 같습니다.

  async function getLatestFileFromGithub(branch, folder) {
    const response = await fetch(
      `https://api.github.com/repos/szxv7704-dot/ai-briefings/contents/${folder}?ref=${branch}`,
      {
        method: 'GET',
        headers: {
          'Authorization': `Bearer ${GITHUB_TOKEN}`,
          'Accept': 'application/vnd.github+json'
        }
      }
    )

    if (response.status === 200) {
      const files = await response.json()
      return files.sort((a, b) => a.name.localeCompare(b.name)).pop()
    }

    if (response.status === 404) {
      return null
    }

    throw new Error(`예상치 못한 응답: ${response.status}`)
  }

여기서 method는 주문 종류(GET, 조회만 하고 아무것도 바꾸지 않겠다는 뜻), 그 아래 주소 문자열은 테이블 번호, headers의 Authorization은 회원 카드, Accept는 "한글 영수증 말고 JSON 형식으로 달라"는 요청입니다. 응답 쪽에서는 response.status가 접수증의 도장 역할을 합니다. 200은 "정상 접수, 음식(파일 목록) 여기 있습니다"이고, 404는 "그런 테이블(폴더)이 아직 없습니다"라는 뜻이며, 이 둘을 구분하지 않고 무조건 response.json()부터 불러버리면 폴더가 없을 때 프로그램이 알 수 없는 이유로 멈춰버립니다. 카카오 로그인 쪽 주문서와 접수증도 형식만 다를 뿐 구조는 같습니다.

  요청 (Kakao 프록시 → 카카오 인증 서버)
    POST https://kauth.kakao.com/oauth/token
    바디 : {
      "grant_type": "authorization_code",
      "client_id": "카카오_앱_키",
      "redirect_uri": "https://my-extension.example/callback",
      "code": "a1b2c3d4"
    }

  응답
    상태 코드 : 200
    바디 : {
      "access_token": "AbCdEf123...",
      "refresh_token": "GhIjKl456...",
      "expires_in": 21599
    }

📝 오늘의 한 줄 정리
어떤 API 호출이든 결국 메서드·주소·헤더·바디로 정확히 채워진 요청서 한 장을 보내고, 상태 코드와 바디로 이루어진 접수증 한 장을 돌려받는 것뿐이며, 이 두 장의 형식을 읽을 줄 알게 되면 처음 보는 API 문서도 더 이상 두렵지 않습니다.

🙋 초보자가 자주 헷갈리는 점
상태 코드를 "200이면 성공, 그 외에는 다 같은 에러"라고 뭉뚱그려 생각하기 쉽습니다. 하지만 404(그런 자원이 없음)와 401(인증 자격이 잘못됨), 500(주방, 즉 상대 서버 자체의 고장)은 원인과 대처법이 완전히 다릅니다. 404가 뜨면 주소나 폴더 이름을 다시 확인해야 하고, 401이 뜨면 회원 카드 격인 토큰을 다시 확인해야 하며, 500이 뜨면 내 코드가 아니라 상대 서버 쪽 문제이므로 잠시 후 다시 시도하는 것이 맞습니다. 상태 코드를 구분하지 않고 뭉뚱그려 처리하면, 정작 고쳐야 할 곳을 못 찾고 엉뚱한 곳을 고치게 됩니다.

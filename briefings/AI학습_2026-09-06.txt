📚 오늘의 학습 주제 : 심화 15일차 · MCP(Model Context Protocol), 도구마다 다른 손잡이를 하나의 규격으로 통일하는 표준 콘센트 (2026-09-06)

📌 어제 배운 내용과의 연결
어제는 셰프(에이전트)가 조리 순서표 없이 스스로 판단해서 도구를 골라 쓴다는 것까지 확인했고, 그 글 끝에서 예고한 대로 오늘은 셰프가 손에 쥐는 그 도구들이 실제로는 서로 다른 회사(Kakao 프록시, GitHub, Google Sheets)에서 만든 물건인데도 어떻게 같은 방식으로 집어 쓸 수 있는지를 살펴봅니다.

🎯 오늘 배울 개념
MCP(Model Context Protocol, AI 에이전트가 외부 서비스에 어떤 도구가 있는지 물어보고 그 도구를 호출하는 방식을 통일해 놓은 공통 규격)가 없다면 에이전트는 서비스마다 완전히 다른 연결 방법을 매번 새로 배워야 한다는 것, 그리고 MCP가 그 문제를 정확히 어느 층위에서 해결하는지

━━━━━━━━━━━━━━━━━━━━

어제 등장한 셰프 비유를 그대로 이어가 봅시다. 셰프가 아무리 판단력이 좋아도, 주방에 있는 프라이팬은 A회사 손잡이, 오븐은 B회사 버튼, 칼은 C회사 잠금장치로 전부 잡는 법과 켜는 법이 다르다면 셰프는 새 도구를 볼 때마다 사용설명서부터 다시 읽어야 합니다. 지금까지의 인터넷 서비스가 딱 이랬습니다. GitHub에 파일을 올리려면 GitHub만의 API 형식과 인증 토큰 방식을 배워야 하고, Google Sheets에 기록하려면 또 다른 인증 방식과 요청 형식을 새로 배워야 했습니다. MCP는 이 모든 도구 제조사가 "우리 도구 손잡이는 전부 이 규격으로 통일하자"고 합의한 표준 콘센트 규격과 같습니다. 집 안의 냉장고든 청소기든 회사가 달라도 똑같은 220V 콘센트에 꽂으면 바로 전기가 들어오듯이, MCP를 따르는 서비스는 회사가 GitHub든 Kakao 프록시든 상관없이 셰프(에이전트)가 항상 같은 두 가지 질문만 던지면 됩니다. "너는 어떤 도구들을 갖고 있니?"(도구 목록 조회) 그리고 "이 도구를 이 입력값으로 실행해줘"(도구 호출)입니다. 도구를 제공하는 쪽을 MCP 서버(MCP Server, 도구 목록과 실행 방법을 표준 규격으로 노출해 두는 프로그램)라 부르고, 그 도구를 불러다 쓰는 에이전트 쪽을 MCP 클라이언트(MCP Client, 표준 규격에 맞춰 서버에게 도구 실행을 요청하는 쪽)라 부릅니다.

🛠 실전 연결
지금 이 브리핑이 만들어지고 저장소에 저장되는 과정 자체가 오늘 배운 개념의 실제 사례입니다. 이 학습 브리핑을 쓰고 있는 에이전트는 여러분의 GitHub 저장소 szxv7704-dot/ai-briefings에 파일을 커밋할 때, GitHub의 원래 API 인증 절차를 직접 배운 것이 아니라 mcp__github__ 라는 접두어가 붙은 표준 도구(create_or_update_file, push_files 같은)를 호출할 뿐입니다. 이 접두어 mcp__github__ 자체가 "github라는 이름의 MCP 서버가 제공하는 도구"라는 뜻입니다. 만약 나중에 Kakao 프록시나 Google Sheets도 MCP 서버로 감싸 놓는다면, 에이전트는 mcp__kakao__, mcp__sheets__ 같은 접두어의 도구를 똑같은 방식으로 호출하면 되고, 여비 계산기의 크롬 확장이 긁어온 영수증을 Kakao 프록시로 보내는 절차와 Google Sheets에 기록하는 절차를 에이전트 입장에서는 완전히 똑같은 모양의 호출로 다룰 수 있게 됩니다. 어제 살펴본 tools 배열 안의 autoApproveTool 같은 도구도, 실제로는 사내에서 직접 만든 함수일 수도 있고 MCP 서버가 제공하는 도구일 수도 있는데, 에이전트 입장에서 둘을 부르는 방식은 구분이 거의 없다는 점이 MCP의 핵심입니다.

🔍 예시
MCP 서버를 등록하는 설정 파일(.mcp.json 또는 claude_desktop_config.json)은 대략 이런 모습입니다.

  {
    "mcpServers": {
      "github": {
        "command": "npx",
        "args": ["-y", "@modelcontextprotocol/server-github"],
        "env": { "GITHUB_TOKEN": "여기에 토큰" }
      },
      "kakao-proxy": {
        "url": "https://your-kakao-proxy.example.com/mcp",
        "transport": "http"
      }
    }
  }

  ＊ github는 명령어를 직접 실행해서 연결하는 방식(command/args),
    kakao-proxy는 이미 떠 있는 웹 주소에 접속하는 방식(url)입니다.
    연결 방법은 서버마다 달라도, 일단 연결된 뒤에는 에이전트가
    두 서버를 부르는 규칙(도구 목록 조회 → 호출)은 완전히 동일합니다.

이렇게 등록된 서버의 도구를 에이전트가 실제로 부르는 순간은 이런 모양입니다.

  도구 이름 : mcp__github__create_or_update_file
  입력값 : {
    "owner": "szxv7704-dot",
    "repo": "ai-briefings",
    "path": "briefings/AI학습_2026-09-06.txt",
    "branch": "learning-log",
    "message": "AI 학습 브리핑 2026-09-06",
    "content": "(오늘 작성한 브리핑 전체 텍스트)"
  }

  ＊ 에이전트는 GitHub의 실제 REST API 주소나 인증 헤더 형식을
    전혀 알 필요가 없습니다. mcp__github__ 서버가 그 뒷단을
    전부 표준 규격 뒤로 숨겨주기 때문입니다.

📝 오늘의 한 줄 정리
MCP는 에이전트가 GitHub든 Kakao 프록시든 서비스마다 다른 연결 방식을 각각 새로 배우는 대신, 어떤 서비스든 같은 방식으로 "도구가 뭐가 있는지 묻고, 실행을 요청하는" 표준 규격이다.

🙋 초보자가 자주 헷갈리는 점
MCP를 AI 모델 자체의 새로운 능력이라고 오해하기 쉬운데, MCP는 모델을 더 똑똑하게 만드는 것이 아니라 모델과 외부 서비스 사이의 연결 통로를 표준화하는 통신 규격일 뿐입니다. 또한 MCP 서버를 연결해 두었다고 해서 에이전트가 그 도구를 언제 써야 하는지 저절로 아는 것도 아닙니다. 어떤 상황에 어떤 도구를 쓰라는 판단 기준은 여전히 시스템 프롬프트나 학습된 지시사항에 담겨 있어야 하며, MCP는 그 판단이 내려진 뒤에 실제로 도구를 실행하는 손 역할만 표준화해 줄 뿐입니다.

💬 내일 예고
내일은 심화 16일차로, 오늘 등록한 도구를 에이전트가 아무 때나 잘못 쓰지 않도록 "언제 어떻게 써야 하는지"를 적어둔 매뉴얼인 스킬(Skill)과, 그 매뉴얼이 실제로 실행되는 작업 환경인 하네스(Harness)가 서로 어떻게 역할을 나누는지 살펴봅니다.

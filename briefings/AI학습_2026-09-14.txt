🎯 오늘 배울 개념
회로 차단기(Circuit Breaker, 짧은 시간 안에 실패가 반복되면 아예 재시도 자체를 잠시 멈춰서 무의미한 재시도가 쌓이는 것을 막는 장치)가 지수 백오프만으로는 부족한 이유, 그리고 멱등성(Idempotency, 같은 요청을 여러 번 보내도 실제로는 딱 한 번만 처리된 것과 같은 결과가 되도록 만드는 성질)이 신청·결제처럼 중복되면 위험한 작업의 재시도를 안전하게 만드는 원리

━━━━━━━━━━━━━━━━━━━━

23일차에서 비서가 카카오 프록시에 전화를 걸다 실패하면 1초, 2초, 4초씩 간격을 늘려가며 다시 거는 지수 백오프를 배웠습니다. 그런데 만약 상대방 사무실이 아예 정전이 나서 전화선 자체가 죽어있다면 어떨까요. 비서가 아무리 간격을 늘려가며 세 번을 다시 걸어도 결과는 매번 똑같이 실패고, 그사이 비서는 다른 일을 하나도 못 합니다. 노련한 비서라면 여기서 한 걸음 더 나아가, "최근 5번 연속으로 전화가 안 됐다"는 걸 스스로 기억해두고, 앞으로 30초 동안은 아예 전화기를 내려놓고 시도조차 하지 않습니다. 이게 회로 차단기의 열림(OPEN) 상태입니다. 30초가 지나면 비서는 딱 한 통만 조심스럽게 다시 걸어보는데(반열림, HALF-OPEN), 이때 연결되면 "정전이 끝났구나" 판단하고 평소처럼 전화를 다시 받습니다(닫힘, CLOSED). 여전히 안 되면 또 30초를 더 기다립니다. 지수 백오프가 "한 번의 요청 안에서 얼마나 기다리며 다시 걸지"를 정하는 규칙이라면, 회로 차단기는 "그 요청 자체를 아예 걸어도 되는 상황인지"를 판단하는 한 단계 위의 규칙인 셈입니다. 한편 멱등성은 전혀 다른 문제를 다룹니다. 비서가 여비 신청서를 접수 창구에 전화로 불러주다가, 상대방이 다 받아 적은 직후에 전화가 툭 끊겼다고 해봅시다. 비서 입장에서는 신청이 접수됐는지 실패했는지 알 수 없으니 다시 걸어 처음부터 불러주고 싶은데, 만약 접수 창구가 이미 다 받아 적어둔 상태였다면 같은 신청이 두 번 접수되어 버립니다. 그래서 노련한 비서는 신청서마다 미리 일련번호(멱등성 키)를 붙여 불러주고, 접수 창구는 "이 일련번호는 이미 처리했다"는 장부를 따로 적어둡니다. 그러면 같은 일련번호로 두 번 불러도 창구는 두 번째부터는 새로 접수하지 않고 첫 번째 처리 결과를 그대로 돌려주기 때문에, 비서가 안심하고 몇 번이든 다시 걸 수 있습니다.

🛠 실전 연결
어제 background.js의 fetchWithRetry는 카카오 프록시 하나에만 걸었지만, 실전에서는 이 함수가 호출하는 대상이 여러 개로 늘어납니다. 예를 들어 여비 계산기 확장이 사내 인트라넷의 "출장신청 제출" API도 같은 fetchWithRetry로 호출한다면, 단순 조회인 카카오 토큰 요청과 달리 이 제출 API는 재시도할 때 반드시 멱등성 키를 함께 보내야 합니다. 그리고 만약 사내 인트라넷 서버 자체가 점검 중이라 계속 실패한다면, 회로 차단기가 없는 지금 코드는 사용자가 페이지를 새로고침할 때마다 매번 세 번씩 헛되이 재시도하며 화면을 몇 초씩 멈추게 만듭니다. 회로 차단기를 background.js 안에 하나 두면, 이런 상황에서 두 번째 새로고침부터는 곧바로 "지금은 서버 점검 중입니다"라는 안내만 보여주고 헛된 재시도를 건너뛸 수 있습니다.

🔍 예시
어제의 fetchWithRetry에 회로 차단기 상태를 얹고, 신청서 제출에는 멱등성 키를 더하면 대략 이런 모습이 됩니다.

  let breakerState = "CLOSED";
  let failCount = 0;
  let openedAt = 0;

  async function fetchWithBreaker(url, options = {}) {
    if (breakerState === "OPEN") {
      if (Date.now() - openedAt < 30000) {
        throw new Error("회로 차단기 열림: 재시도 건너뜀");
      }
      breakerState = "HALF_OPEN";
    }
    try {
      const res = await fetchWithRetry(url, options);
      breakerState = "CLOSED";
      failCount = 0;
      return res;
    } catch (err) {
      failCount++;
      if (failCount >= 5) {
        breakerState = "OPEN";
        openedAt = Date.now();
      }
      throw err;
    }
  }

  function submitTravelExpense(payload) {
    const idempotencyKey = crypto.randomUUID();
    return fetchWithBreaker("/api/travel-expense", {
      method: "POST",
      headers: { "Idempotency-Key": idempotencyKey },
      body: JSON.stringify(payload),
    });
  }

submitTravelExpense는 매번 새 일련번호(idempotencyKey)를 발급해 딱 한 번 붙여 보내고, 이후 fetchWithBreaker 안의 재시도는 같은 번호를 그대로 유지한 채 다시 시도하므로, 서버는 같은 번호가 두 번 들어와도 첫 처리 결과만 돌려주고 중복 접수를 막습니다.

📝 오늘의 한 줄 정리
지수 백오프가 한 번의 요청을 얼마나 끈질기게 다시 걸지를 정하는 규칙이라면, 회로 차단기는 그 요청 자체를 계속 걸어도 되는지를 판단하는 규칙이고, 멱등성은 그렇게 여러 번 걸어도 결과가 딱 한 번만 처리된 것처럼 안전하게 만드는 규칙입니다.

🙋 초보자가 자주 헷갈리는 점
회로 차단기를 재시도 로직과 같은 것으로 착각하기 쉬운데, 재시도는 "한 번의 요청을 성공시키려는 노력"이고 회로 차단기는 "그 노력 자체를 언제 멈출지 정하는 상위 판단"이라 서로 다른 층위입니다. 또한 멱등성 키를 붙이면 재시도가 무조건 안전해진다고 생각하기 쉬운데, 서버 쪽에서 그 키로 처리 여부를 기록하고 확인하는 로직을 따로 만들어두지 않으면 키를 아무리 보내도 소용이 없다는 점, 즉 멱등성은 클라이언트 혼자만의 약속이 아니라 서버와 함께 지켜야 하는 약속이라는 점이 자주 놓치는 부분입니다.
